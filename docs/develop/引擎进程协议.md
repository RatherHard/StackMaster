## 一、定位与不变式

引擎进程协议是计划书 5.6 的**第 4 类契约**:编排器 / verifier ↔ Rust `vm-worker` 的进程边界 JSON 协议。与既有三类契约的关系:

1. **不另造私有格式**(投影与错误契约语义 §5.3):worker 的投影、错误与增量消息形态即 `PublicStateProjection` / `PublicError` / `ProjectionDelta`;动作面即 `ActionRequest` / `ActionResponse`;装载面即私有判题包 Schema。编排器对 vm-worker 输出**按同一契约重新校验**(5.6)后才能进入下发通道。
2. **本文新增的只有传输信封**:帧格式(§三)、命令判别式与 `seq`(§四)、快照信封(§四)。这些是进程协议本体,不是对浏览器契约的改写;浏览器侧永远看不到本协议的任何帧。
3. **进程边界纪律**(ADR-3 / CLAUDE.md):TS 与 Rust 只经 spawn + stdio JSON 通信,禁止 FFI / N-API;worker 无网络、无子进程,文件系统访问仅限进程运行所必需。
4. **秘密零驻留**(ADR-7;数据分类清单):`VmState`、私有题目包、隐藏测试、seed 只存在于 worker 进程内。worker 的**一切输出**(stdout 帧、stderr 日志)只含公开面;`loaded` 回执只携带身份与版本字段(与公开描述包同源),不含 seed、secrets、judging、IR 等任何私有内容。
5. **单会话单进程**(ADR-3):一个 worker 进程服务一个会话;强制终止后进程不复用,恢复走快照替换(§四 import_snapshot;编排器侧驱动归 WP-8)。
6. **确定性**(I-4):一切拒绝路径(帧层、信封层、命令级)都是 `(输入, 进程状态)` 的确定性函数,同一输入恒产生字节相同的响应;禁止按隐藏状态分支改变拒绝行为。

## 二、版本与编号空间(登记)

### 2.1 登记(5.6;版本策略 §二——阶段一验收评审 §三移交项 3 收口)

| 项 | 值 |
|---|---|
| 版本号 | **`ENGINE_PROCESS_PROTOCOL_VERSION = 1`** |
| 编号空间 | **独立**(不与会话动作协议、嵌入协议、双包 Schema 共用) |
| TS 载体 | `packages/protocol/src/version.ts`(唯一登记处) |
| Rust 镜像 | `vm-engine/vm-worker` → `vm_worker::protocol::version::ENGINE_PROCESS_PROTOCOL_VERSION` |
| 双侧防漂移 | `vm-worker` 测试断言 TS 常量与 Rust 常量同值(文本比对) |
| 传输载体 | worker 启动 `ready` 帧自报 `protocolVersion`(§四) |

### 2.2 与会话动作协议版本的关系

- Schema 面(`ActionRequest` / `ActionResponse` / `PublicStateProjection` / `ProjectionDelta` / `PublicError` / `PublicEvent`)随**会话动作协议**版本(`SESSION_ACTION_PROTOCOL_VERSION = 1`)演进,worker 以 `ActionRequest.protocolVersion` 的 Schema `const` 校验受理面;
- **引擎进程协议版本**覆盖:帧格式、命令信封、命令语义、快照信封,以及"该 worker 受持哪一版 Schema 面"。Schema 面的破坏性变更(会话动作协议版本递增)要求 worker 重新接线,因此**联动递增**引擎进程协议版本;
- 版本错配处置(fail-closed,版本策略 §四"宁可拒绝"):编排器 spawn worker 后读取 `ready.protocolVersion`,与自身常量不一致即**拒绝建立会话**并回收进程——不近似执行、不做运行时协商降级;
- N-1 窗口语义:进程协议双方同部署,窗口由"编排器同时能按 N 与 N-1 语义解释 `ready` / 命令面"实现(部署期双形态支持),窗口时长为实现期运维参数(阶段三);窗口结束下线旧版属于显式运维动作(版本策略 §五)。

### 2.3 引擎自报版本与锁定

- `ready` 帧同时自报 `vmEngineVersion`(= 二进制 crate 版本)与 `engineBuildId`(编译期 `VM_ENGINE_BUILD_ID` 注入,缺省 `dev`);
- 装载时 worker 比对私有包声明:`vmEngineVersion` 不一致,或声明了 `engineBuildId` 且不一致 → 拒绝装载(`challenge_invalid` 方向,§四 load);快照导入同锚(§四 import_snapshot)。版本锁定语义 = 版本策略 §四,worker 侧强制是其进程级落点。

## 三、帧格式(冻结)

### 3.1 决策记录 D-F1:行分隔 JSON(NDJSON)

**决策**:stdio 采用**行分隔 JSON**——一帧 = 一个 UTF-8 编码的 JSON 对象 + 恰一个 LF(0x0A)行界。

**理由**:JSON 文本规范中字符串内 LF 必为 `\n` 转义(RFC 8259 §7),裸 LF 不可能出现在合法帧载荷内,因此行边界即帧边界,无歧义;stdio 管道是字节流,逐行读取与解析器天然契合;一行一帧可读可调试,fixture 与测试直接以文本形态表达。**否决长度前缀帧**:二进制帧头引入帧长字段自身的边界与字节序问题,对 JSON 载荷没有额外表达力,MVP 无收益;若 benchmark 证明需要零拷贝或帧内二进制(计划书 10.1 的 benchmark 证据要求),按协议版本演进,不在 v1 预留。

推论与细则:

- **帧内禁止裸 LF**(序列化器不变式;worker 写侧防御性断言,见 `FrameWriter::serialize_frame`);
- LF 前的 CR 是合法 JSON 空白(CRLF 形态被容忍,但不是规范形态;发起方应只发 LF);
- 空行(空载荷)= 畸形帧,拒绝;
- 帧载荷为**紧凑 JSON**(零空白)是 worker 写侧的规范形态;读侧对空白宽容(JSON 语法允许)。

### 3.2 决策记录 D-F2:单帧上限

**决策**:`MAX_FRAME_BYTES = 16 MiB`(16 × 1024 × 1024 字节,按帧载荷计,不含行界 LF)。

**推导**:最大合法帧是快照导出——教学规模 `VmState`(计划书:每会话个位数 MB 宿主内存,VMA 区域为 4KB 倍数的少数几个区域)的十六进制展开 + 信封开销;16 MiB 对该规模留有充分余量,同时仍是硬上界。**双向强制**:读侧缓冲到达上限即失败(不等待行界、不消费后续字节);写侧序列化结果超限即引擎故障,fail-closed 终止,不静默截断。快照分块导出是协议版本演进选项,benchmark 证据前不引入。

### 3.3 帧边界与半包处理(fail-closed)

读侧(`FrameReader`)逐字节缓冲,以下情形全部**立即失败**,不得"尽力解析":

| 情形 | 判定 |
|---|---|
| 行界前载荷字节 > `MAX_FRAME_BYTES` | 超限,立即失败(不等待 LF) |
| EOF 时缓冲非空 | 半包(截断帧) |
| 载荷非合法 UTF-8 | 非 UTF-8 |
| 载荷非合法 JSON 语法(含空行、尾随垃圾) | 畸形 JSON |
| 对象出现重复键(按转义解码后的精确拼写比较,`"a"` 与 `"\u0061"` 同键) | 重复键 |
| 字符串含孤立代理项(serde_json 解析层拒绝;高位未配对与孤立低位两形态) | 孤立代理项 |
| 顶层不是 JSON 对象 | 非对象 |

### 3.4 方向与错误通道

- **stdin(编排器 → worker)**:只承载命令帧(§四),一行一命令,stop-and-wait(发一帧、等一帧响应,§4.6);
- **stdout(worker → 编排器)**:只承载协议帧(`ready` / 命令响应 / `protocol_error`)。**任何日志写 stdout 都是协议违规**——stdout 纯净性有机检(集成测试逐行断言 stdout 可解析为协议帧);
- **stderr(worker → 宿主)**:仅受控日志。一行一条、`[vm-worker]` 前缀、只含事件与错误码;**禁止携带** `VmState`、私有包内容、seed、隐藏测试、隐藏判题细节、内部堆栈与文件路径(数据分类清单 §九;秘密零驻留的输出面落点)。受控日志不进入任何公开响应(9.1);
- worker 写侧在写出前对响应帧做**契约自检**(如 `ActionResponse` 对冻结 Schema 复验);自检失败 = 引擎缺陷,按协议层违规处置(`contract_inconsistency`),不把非法形态发上管道。

### 3.5 协议层违规处置(§六表)

一切协议层违规(帧层 + 信封层 + 状态机层)fail-closed:

1. worker 尽力而为输出一帧 `protocol_error`(带违规码;帧同步不可信时不承诺成功);
2. stderr 写一条受控日志(事件 + 错误码,无载荷内容);
3. 进程以**非零退出码**终止,进程不复用;恢复由编排器走快照替换路径(WP-8)。

**裁决依据**:帧同步或信封语义一旦失真,后续帧不可信,继续运行只扩大不确定行为;响亮失败使版本错配与编排器缺陷在第一帧即暴露。

## 四、命令面(冻结)

### 4.0 生命周期状态机

```text
spawn → ready(自报版本)→ load(锁定题目)
      →(可选)import_snapshot(崩溃替换恢复;两步 = load + import)
      → apply_action / query_projection / export_snapshot 循环(单会话串行)
      → shutdown → 退出码 0
```

- `seq`:编排器签发的命令序号,自 1 起**严格递增**;worker 校验 `seq == 上一条 + 1`,违规 = `sequence_violation`(协议层,§3.5);
- **stop-and-wait**:worker 逐帧处理、逐帧应答,v1 不支持流水线(单会话串行的进程级表达;并发是编排器队列的职责,WP-8);
- 状态机违规(未装载即发动作 / 查询 / 快照命令、装载成功后重复 load)= `state_violation`(协议层,§3.5);
- stdin 干净 EOF(无半包)= 优雅退出(等价 shutdown);进程间无 in-flight 帧。
- **骨架阶段行为**:WP-1 交付的协议骨架完整实现帧层、信封、状态机与载荷契约校验;VM 执行、投影生成与快照内容归 WP-3 ~ WP-8 接线。骨架对**通过全部契约校验**的合法命令返回确定性的命令级错误 `internal_error`(不执行、不推进 revision),这不构成对协议语义的偏离。

### 4.1 `ready`(worker → 编排器,启动自报)

```json
{"type":"ready","protocolVersion":1,"vmEngineVersion":"0.1.0","engineBuildId":"dev"}
```

worker 写出本帧后才读命令。编排器侧动作:比对 `protocolVersion`(§2.2)、记录 `vmEngineVersion` / `engineBuildId`(版本策略 §四记录项 #3 的运行时来源)。

### 4.2 `load`(编排器 → worker)

```json
{"type":"load","seq":1,"privateBundle":{…私有判题包…},"sessionSeedHex":"…"}
```

- `privateBundle`:完整私有判题包对象,worker 按 `private-bundle.schema.json` + 语义承接 + 类型镜像三重校验(§5.1);跨包语义(XS-\* 检查器、双程序形态恰一)由装载链上游(challenge-compiler / 编排器,WP-2)把关,worker 按单包 Schema 复验;
- `sessionSeedHex`(可选):`seedPolicy.strategy = server_random_per_session` 时**必填**——编排器生成的 CSPRNG 会话种子(WP-6 决策:种子在编排器生成、按会话锁定、worker 只消费;派生路径写入回放元数据,**不含 seed 值**);`fixed` 时**禁止**携带(seed 在包内 `seedPolicy.seedHex`)。形态 `^([0-9a-fA-F]{2}){8,32}$`,与包内 seedHex 同锚;
- **成功** → `loaded` 回执:

```json
{"type":"loaded","seq":1,"loaded":{"challengeId":"…","challengeContentVersion":"…","vmProfileVersion":"…","dslSchemaVersion":2,"vmEngineVersion":"0.1.0","engineBuildId":"dev","initialRevision":0}}
```

- **失败** → 命令级错误 `challenge_invalid`(宁可拒绝装载,不近似执行;版本策略 §四):Schema / 语义 / 镜像校验失败、seed 互斥违反、形态非法、`vmEngineVersion` / `engineBuildId` 锁定不一致。装载失败后进程存活、阶段保持未装载,重装载行为确定(同一输入恒同结论);
- **版本记录项**(版本策略 §三):装载成功即锁定 #3(引擎构建 ID,自报与声明一致)+ 包哈希(编排器侧对原始字节计,不在本协议传输)。

### 4.3 `apply_action`(编排器 → worker)

```json
{"type":"apply_action","seq":2,"requestId":"…","actionRequest":{…完整 ActionRequest…}}
```

- `actionRequest`:**完整冻结信封**(6 字段 + 12 动作判别式,会话动作协议语义 §二 / §三)。编排器已完成认证 / 幂等 / `baseRevision` 预校验(§5.2),worker 对载荷按同一契约**重新校验**(6.2 第 6 条:地址可见性、区域权限、操作数与资源预算的权威校验点在执行域内);
- `requestId`:编排器签发的服务端请求 ID(D-F4),形态 `^[A-Za-z0-9_-]{1,128}$`;worker **原样回传**,使 worker 输出即完整 `ActionResponse`,编排器按 `action-response.schema.json` 复验后可直接进入下发通道(投影与错误契约语义 §5.3);
- **载荷级拒绝**(Schema / 语义校验失败)= 确定性 `ActionResponse`:

```json
{"type":"action_response","seq":2,"actionResponse":{"requestId":"…","revision":0,"status":"rejected","projectionDelta":null,"publicEvents":[],"userVisibleError":{"code":"invalid_input_format","message":"action payload failed contract validation"}},"checkpointExport":null}
```

  即 §4.5 协议级拒绝行:revision 不变、delta null、事件空、`userVisibleError` 必有;错误码 `invalid_input_format`,message 为静态模板(不含校验器原始文本与字段路径——校验基线 #8);worker 保持存活,会话继续;
- **成功执行** → `action_response`,其中 `actionResponse` 为完整 `ActionResponse`(`status` / `revision` / `projectionDelta` / `publicEvents` / `userVisibleError` 按执行语义生成,WP-4 / WP-7);`checkpointExport` 仅当本动作为 `create_checkpoint` 且成功时非 null(§4.7);
- **undo / checkout_checkpoint / reset / pause / create_checkpoint / step / run_to_event** 等:**经 `apply_action` 走 12 动作判别式,不设独立命令**(D-F6:它们本来就是会话动作协议的冻结动作,独立命令 = 另造私有格式)。

### 4.4 `query_projection` / `export_snapshot` / `import_snapshot`

```json
{"type":"query_projection","seq":3}
{"type":"export_snapshot","seq":4}
{"type":"import_snapshot","seq":5,"snapshot":{…快照信封…}}
```

- `query_projection` → `{"type":"projection","seq":…,"projection":{…完整 PublicStateProjection…}}`;服务对象:会话创建的初始投影、快照导入后的重同步取数(`sync-projection` 的**缓存重发**是编排器行为,不触发 worker 往返,§5.2);
- `export_snapshot` → `{"type":"snapshot_exported","seq":…,"snapshot":{…}}`;编排器将快照存为崩溃恢复点(PostgreSQL,阶段三持久化);
- `import_snapshot` 的载荷为**快照信封**(D-F5):

```json
{"snapshotFormatVersion":1,"vmEngineVersion":"0.1.0","engineBuildId":"dev","revision":0,"payload":{…}}
```

  信封字段冻结如上;`payload` 内容形态归 **WP-6**(COW 快照序列化),本协议只做信封与版本绑定校验:`snapshotFormatVersion = 1`、双版本与 worker 自报一致、`payload` 为对象,任一不满足 = 命令级错误 `challenge_invalid`;
- **崩溃替换恢复**(9.1;WP-8 驱动):worker 被强制终止后,编排器 spawn 新进程,按序 `load`(私有包)→ `import_snapshot`(最近服务端快照)→ `query_projection`(取当前投影供 `sync-projection` 重发)。两步恢复让"内容状态"与"题目 / 判题上下文"各归其位。

### 4.5 `shutdown`

```json
{"type":"shutdown","seq":6}
```

worker 冲刷 stdout、回 `shutdown_ack` 后以**退出码 0** 结束。close-session 的 worker 侧落点;进程不复用。

### 4.6 响应帧汇总(冻结)

| `type` | 场景 | 载荷字段 |
|---|---|---|
| `ready` | 启动自报 | `protocolVersion`、`vmEngineVersion`、`engineBuildId` |
| `loaded` | load 成功 | `seq`、`loaded{challengeId, challengeContentVersion, vmProfileVersion, dslSchemaVersion, vmEngineVersion, engineBuildId, initialRevision}` |
| `action_response` | apply_action | `seq`、`actionResponse`(完整冻结信封)、`checkpointExport?` |
| `projection` | query_projection | `seq`、`projection`(完整 `PublicStateProjection`) |
| `snapshot_exported` | export_snapshot | `seq`、`snapshot`(快照信封) |
| `snapshot_imported` | import_snapshot 成功 | `seq` |
| `shutdown_ack` | shutdown | `seq` |
| `command_error` | 命令级失败 | `seq`、`error{code, message}` |
| `protocol_error` | 协议层违规(尽力而为) | `code`、`seq?` |

一切响应帧 `seq` = 对应命令的 `seq`(`ready` / 无关联的 `protocol_error` 除外)。信封一律未知字段拒绝(`deny_unknown_fields`):未知命令判别式 = `unknown_command`、信封含未声明字段 / 缺 `seq` / 字段类型不符 = `envelope_invalid`(协议层,§3.5)。

### 4.7 checkpoint 的 ID 与快照回传(D-F6 / D-F7)

- `checkpointId` 由 **worker 签发**(create_checkpoint 成功时,形态遵循服务端标识符字符集),经 `action_response.checkpointExport` 回传:`{"checkpointId":"…","snapshot":{…快照信封…}}`——checkpoints 的 COW 快照随回执落编排器账本,成为崩溃恢复点;
- `list-checkpoints` 是编排器账本查询(会话动作协议语义 §5.1),不进 worker;`checkout_checkpoint` 经 `apply_action` 携带 `checkpointId`,worker 从**本进程内**快照表解析;
- 崩溃恢复后,旧 checkpoint 引用随进程消失:新进程持有"最近服务端快照"的内容,时间线的 checkpoint 粒度恢复属于编排器账本与 WP-8 的职责边界(协议层如实记录该退化)。

## 五、职责切分表

### 5.1 会话命令归属(编排器侧命令 ↔ worker 命令)

| 编排器会话命令(9.1 / 会话动作协议语义 §5.1) | worker 侧落点 | 说明 |
|---|---|---|
| `create-session` | spawn → `ready` 比对 → `load` → `query_projection` | 认证、租户配额、token 绑定、题目版本解析、会话签发都是编排器职责;worker 只负责装载与版本锁定 |
| `action`(12 动作) | `apply_action` | 编排器预校验(基线 #1–#5)+ 入队串行;worker 重校验(#6)+ 执行 + 投影生成(ADR-7) |
| `list-checkpoints` | **无 worker 往返** | 编排器 checkpoint 账本(由 `checkpointExport` 回执驱动) |
| `sync-projection` | **无 worker 往返** | 编排器重发最近缓存投影;仅快照导入后需 `query_projection` 取数 |
| `submit` | **无直接 worker 命令** | 提交引用编排器记录的规范化动作日志;独立 verifier 复用同一回放引擎重放(ADR-8),verifier ↔ 回放库是进程内消费,不经本协议(阶段六接线) |
| `close-session` | `shutdown` | 编排器回收进程;超时 / 强制终止路径见 WP-8(资源面) |

### 5.2 服务端校验基线落点(会话动作协议语义 §七)

| # | 基线 | 落点 |
|---|---|---|
| 1 | 认证上下文派生身份 | 编排器(阶段二以可注入接口桩替身,WP-8);请求帧不含身份字段 |
| 2 | token 绑定校验 | 编排器(同上) |
| 3 | `baseRevision` 校验 | 编排器预检(4.2 拒绝规则);worker 维护权威 revision 账本并回传 |
| 4 | `idempotencyKey` 防重 | 编排器(幂等窗口缓存**字节相同**的最终响应;负载比较按规范化序列化——worker 无幂等职责) |
| 5 | 单会话串行 | 编排器会话队列;worker stop-and-wait 帧序(§4.0)是第二道闸 |
| 6 | 动作参数 / 地址 / 权限 / 操作数 / 预算重校验 | **worker**(执行域内权威校验点;协议层上限是外圈护栏) |
| 7 | 只从服务端题目包和服务端状态执行 | 协议无状态上载通道:信封 `deny_unknown_fields` + `ActionRequest` Schema `additionalProperties: false`,自制状态字段直接被拒(ZR-T2) |
| 8 | 校验失败响应面 | worker 拒绝响应 = 冻结 `PublicError` 形态 + 静态模板 message,无校验器内部细节;原始载荷仅进受控日志 |

### 5.3 一次动作的端到端数据流(计划书 5.3 映射)

```text
1. 浏览器 ActionRequest ──HTTPS/WSS──▶ 编排器(认证 / 幂等 / revision 预检,基线 #1–#5)
2. 编排器入队 ──apply_action 帧──▶ 绑定会话的 worker
3. worker 重校验(#6)→ 私有包 + 当前 VmState 执行 → 追加私有事件与规范化动作日志(WP-4 / WP-6)
4. worker 判定权威目标条件与资源预算(WP-5)
5. worker 按 ProjectionPolicy 生成 PublicStateProjection / ProjectionDelta(WP-7,ADR-7:脱敏在离开执行域之前)
6. worker ──action_response 帧──▶ 编排器:按冻结 Schema 重新校验 → 更新 revision 账本(requestId 关联)→ WSS 下发浏览器
7. 提交时 verifier 重放规范化动作日志(ADR-8 同一份回放代码)
```

## 六、错误与退出语义

### 6.1 错误码词汇(冻结)

| 层 | 词汇 | 说明 |
|---|---|---|
| 命令级错误(`command_error.error.code`) | **PublicError 16 码 ∪ `challenge_invalid`** | 复用冻结枚举(错误类型也是契约,5.6);`challenge_invalid` 是装载 / 快照方向的拒绝(版本策略 §四的结果类型方向),非 PublicError 码,故在命令级词汇扩一格;`message` 为确定性静态模板 |
| 载荷级拒绝(`action_response.status = rejected`) | `userVisibleError.code` ⊆ PublicError 16 码 + 能力矩阵 | 骨架固定 `invalid_input_format`;执行面可解释错误按能力矩阵生成(WP-7 错误粗化生成器) |
| 协议层违规(`protocol_error.code`) | 本节违规码表 | 传输诊断,非浏览器可见面 |

协议层违规码表(与实现 `ProtocolViolation::code()` 同串):

`frame_too_large` / `truncated_frame` / `invalid_utf8` / `malformed_json` / `duplicate_key` / `lone_surrogate` / `not_an_object` / `io_error` / `unknown_command` / `envelope_invalid` / `sequence_violation` / `state_violation` / `contract_inconsistency`

### 6.2 退出码

| 退出码 | 含义 | 编排器处置 |
|---|---|---|
| `0` | `shutdown_ack` 后优雅退出,或 stdin 干净 EOF | 正常回收 |
| 非 `0` | 协议层违规、IO 故障或进程内缺陷(含启动期 Schema 编译失败) | 不复用进程;会话失败 → 快照替换恢复路径(WP-8) |

### 6.3 秘密与值级纪律(输出面)

- stdout 帧只含公开面字段;`loaded` 回执的字段集与公开描述包同源(§4.2);
- stderr 只含事件与错误码(§3.4);错误码与 message 都不携带校验器路径、载荷摘录、内部堆栈(校验基线 #8);
- 一切响应先经冻结 Schema 自检再上管道(§3.4);出站 `ActionResponse` 的 `explanation` / `addressHex` 能力矩阵合规由 WP-7 生成侧保证,ZR-P6 机检承接。

## 七、决策记录

| # | 决策 | 内容与理由 |
|---|---|---|
| D-F1 | 帧形态 = NDJSON | 行界即帧界(JSON 字符串内 LF 恒转义,无歧义);长度前缀被否决(无表达力收益、引入帧头边界问题);演进走协议版本(§3.1) |
| D-F2 | 单帧上限 16 MiB | 快照导出是最大合法帧;教学规模推导,双向强制,超限 fail-closed;分块导出为演进选项(§3.2) |
| D-F3 | stdout 纯净性机检 | 日志误写 stdout 会破坏帧同步,故"stdout 每行皆协议帧"作为进程级测试断言,而非约定(§3.4) |
| D-F4 | `requestId` 编排器签发、命令帧注入 | worker 回传完整 `ActionResponse`,编排器 Schema 复验后直通下发通道;避免"缺一字段的私有变体"(§4.3) |
| D-F5 | 快照信封版本化 | `snapshotFormatVersion` + 引擎双版本绑定;`payload` 形态归 WP-6,传输面先冻结(§4.4) |
| D-F6 | undo / checkout / reset 不设独立命令 | 它们是会话动作协议冻结动作;独立命令 = 私有格式,违背 5.6 复用纪律(§4.3) |
| D-F7 | 协议层违规一律终止、进程不复用 | 帧同步 / 信封语义失真后,后续通信不可信;响亮失败 + 快照替换恢复(§3.5) |
| D-F8 | 两步崩溃恢复(load + import_snapshot) | 题目 / 判题上下文与内容状态分离装载;恢复后旧 checkpoint 引用退化由编排器账本承接(§4.4 / §4.7) |
| D-F9 | 会话种子由编排器生成传入 | `server_random_per_session` 的 CSPRNG 在编排器侧生成、按会话锁定,worker 只消费;seed 零驻留边界与回放元数据语义归 WP-6(§4.2) |
