## 〇、修订原则(先立规矩,再改字)

1. **底线 1 / 2 / 3 一字不动** —— 本次改版不触碰「VM Core 与隐藏判题信息隔离」「浏览器只收脱敏投影」「服务端串行权威」三条。
2. **底线 4 只改「分发形态」那半句**,另两半(DSL 不执行宿主代码、Core/UI/协议/适配层解耦)**保留原意**。
3. **`iframe` 的「安全原理」不能跟着一起删** —— 计划书 §8.1 里真正有价值的两句话(「前端隔离机制**不保护**客户端秘密」「Shadow DOM / Web Component **不是**安全边界」)是**通用原理**,页面分发下**依然成立**,须**保留**(否则会丢掉一条重要的安全纪律)。
4. **区分「退役」与「删除」** —— 凡涉及 `packages/embed-runtime` / `react-wrapper` / `web-component` / `apps/plugin-dev` / `docs/contracts/嵌入协议.md` 的表述,标**退役**并给替代,不在同一批里删代码。
5. **不得借修订扩权** —— 本次修订**只**落实 §五 的四项定案,不顺手改别的口径。

### T1 术语订正(回答主控提问「宿主是什么?不是说独立页面吗?」)

主控提问成立 —— 独立页面下**不存在「宿主页面」**。本仓库的「宿主」实为**三个不同义项**被混用:

| 义项 | 含义 | 处置 |
|---|---|---|
| **宿主页面** | 嵌 iframe 的那个第三方页面(与插件共享 DOM / 执行上下文) | **退役** —— 独立页面下结构性不存在 |
| **宿主 / 宿主平台** | **服务端集成方(平台 / 靶场)**:`宿主平台接入指南` / `宿主成绩同步` / `host backend token` / `/host/scores` | **保留** —— 它只与 **API** 交互,**不与页面共享任何运行环境** |
| (第三义项)**宿主代码** | 底线第 4 条前半句里的「宿主」= **运行环境**(DSL 不得执行宿主环境代码) | **原样保留,不得混改** |

**行文规则**:
1. 涉及**页面**处**不得**再用「宿主」二字(历史留档除外);R6 的「宿主平台不需要安装前端依赖」⇒ 改为「**平台侧不需要安装任何前端依赖**」;
2. 涉及**服务端集成方**处可用「宿主平台 / 平台 / 靶场」,并在首次出现处定义为「**平台 / 靶场(服务端集成方:只与 API 交互,不与页面共享运行环境)**」;
3. **底线第 4 条前半句的「宿主代码」一个字都不许动** —— 它与上面两个义项都不同义。

### L1 底线第 4 条最终措辞(**计划书 `:1044` 与 `CLAUDE.md` 逐字一致**)

> 4. **题目 DSL 不执行任意宿主代码，以与 API 同源的独立页面分发（不提供与第三方页面共享 DOM 或执行上下文的嵌入形态），并保持 Core、UI、协议和平台适配层解耦。**

**为什么这样写**(与原文对照):
- 「不执行任意宿主代码」「保持 Core、UI、协议和平台适配层解耦」—— **原样保留**(底线 1 / 2 / 3 与另两半句不属本次改版);

- 括号内「**不提供与第三方页面共享 DOM 或执行上下文的嵌入形态**」= 这条底线的**安全内核**:把「实验室不得与第三方页面共享运行环境」写成**禁止式**约束 —— 既是当前形态的陈述,也是**对未来嵌入方案的禁令**(与方案 B「不保留口子」一致);
- **无「默认」二字**(方案 B)⇒ 将来若要恢复嵌入形态,**必须改底线本身**。

### R1 · 产品定位第一句(`docs/项目计划书.md:7`)

**原文(逐字)**:
> 一个可嵌入、可回放、可解释的 Pwn 概念实验室，而不是浏览器中的完整 Linux 或 x86 模拟器。

**拟改**:
> 一个**可链接、可回放、可解释**的 Pwn 概念实验室，而不是浏览器中的完整 Linux 或 x86 模拟器。

**理由**:「可嵌入」直接指向插件形态,已由 §五 定案退役。改为**可链接**——平台以**下发地址**的方式引入(§五 5.2),不再嵌入宿主页面。

**风险**:「可链接」比「可嵌入」弱(不再能嵌进宿主 UI 与其他面板并排)。**这是本次改版已接受的产品代价**(插件形式退役的必然后果),须主控确认可接受。

### R6 · 第八章标题与 8.1(`docs/项目计划书.md:670` / `:672`)

**原文(逐字)**:
> ## 八、插件嵌入、协议与部署
> ### 8.1 默认嵌入形态
> 默认采用跨域、独立来源的 iframe：
> - 宿主平台不需要安装前端依赖；
> - 避免宿主 CSS 污染插件；
> - 插件可以独立发布、升级和回滚；
> - 兼容不同语言和前端框架；
> - 插件异常时较少影响宿主页面。

**拟改**:
> ## 八、页面分发、协议与部署
> ### 8.1 默认分发形态:**独立页面**
> 默认采用**与 API 同源的、由服务端签发地址的独立顶层页面**(不再采用 iframe 嵌入):
> - 宿主平台**不需要安装任何前端依赖** —— 只需调签发端点并把地址下发;
> - **不存在宿主 CSS 污染问题** —— 页面不在宿主 DOM 内;
> - 页面可**独立发布、升级和回滚**,与宿主解耦;
> - **天然兼容不同语言与前端框架** —— 宿主只需能跳转/展示一个 URL;
> - **页面异常与宿主页面互不影响** —— 无共享执行上下文。
> **原 iframe 形态的下列理由已随之退役**(仅作历史留档):iframe `sandbox` 最小权限、`event.origin` / `event.source` / `targetOrigin` 校验、opaque origin 与 `MessageChannel` 绑定等 —— 这些是**嵌入协议**(V-1~V-13)的实现要点,**随协议整体退役**。

**理由**:§五 定案。**注意**:原 5 条理由中有 4 条**在页面形态下依然成立**(不需依赖 / 无 CSS 污染 / 独立发布 / 兼容语言框架 / 异常隔离),所以**不是推翻,而是换机制达到同样目的** —— 这一点应在正文写明,避免读成「能力缩水」。

**风险**:iframe 的 `sandbox` 隔离**确实消失**了(那是 iframe 独有的)。须在 §8.1 明确:**替代隔离来自「页面与宿主不同执行上下文」这一事实本身**,以及**宿主页面从未获得任何权限**。

### R7 · 安全原理两段(`docs/项目计划书.md:684` / `:686`)—— **建议保留原理,只退役 iframe 专属部分**

**原文(逐字)**:
