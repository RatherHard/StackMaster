# 阶段五 WP-51 决策草稿(embed-runtime 宿主侧 SDK 与 react-wrapper)

> 状态:实现期草稿(2026-09-11,WP-51 交付时成文)。**本文不是权威决策记录**:正式 D-API 增补、嵌入协议状态行、compose 走查路径登记由 WP-56 统一收尾回填;本文供 WP-52(插件 Shell)复用接口面与 wire 形态、供 WP-55(E2E 与门禁)对接模拟页,并作为 WP-56 回填的事实来源。

## 一、Q4 定案:V 规则引擎落点 = 协议解析器同源 + 核心规则编排单实现 isomorphic 复用

**任务分解 §六 Q4**(embed-runtime isomorphic 双侧消费 vs 宿主/插件各自实现)定案:**分层同源**——

1. **消息契约层(已同源,零新决策)**:`EmbedMessageSchema`、方向集常量、能力枚举、主题三值全部消费 `@stackmaster/protocol` 公开入口,宿主与插件天然共享同一解析器(protocol 包是契约单一来源,WP-5 已冻结),不存在漂移面。
2. **V 规则编排层(本次定案)**:**可抽取为纯函数 / 纯类的部分单实现双侧消费**,宿主或插件独有的部分各自持有编排。具体落点:
   - **双侧复用(本包导出的纯函数 / 无宿主状态的构件)**:版本协商 `negotiateEmbedProtocolVersion`(max-wins 纯函数;WP-52 插件侧按同一语义解释自身 supportedVersions)、esid 生成/校验 `generateEmbedSessionId` / `validateEmbedSessionId`(插件侧虽不生成,但 fragment 校验可复用)、按类型滑动窗口限速器 `TypeRateLimiter`(V-10 双侧同构:D-API-77 两个频率参数同款语义)、违规计数键 `VIOLATION_COUNTER_KEYS`(键集以规则编号为前缀,双侧计数面同键名,13.3 E2E 可用同一断言词汇);
   - **宿主独有(embed-runtime EmbedSession 私有编排,不导出给插件复用)**:V-1/V-1'(来源/source 三重绑定)、V-5(esid 全等 + 窗口绑定)、V-7 高水位的"接收端"角色、能力授予(granted ⊆ hello.capabilities)、T_handshake 宿主侧超时、port 转移发送面;
   - **插件独有(WP-52 自实现)**:V-5 的"发起方"角色(fragment 读取)、V-7 高水位的插件侧维护、ready/theme_changed/language_changed 的接收校验、能力降级三行(§4.4 插件义务)、宿主 origin 钉住。
3. **理由**:协议解析器已同源,分歧仅在 V 规则编排层(任务分解原文)。编排层中真正"双侧同构"的只有限速、计数、协商三个无状态构件——对它们单实现可消除漂移且零耦合(都是纯函数/纯类,不携带宿主会话状态);其余规则的角色是**非对称的**(宿主是接收端+授予方,插件是发起方+被授予方),强行共享一个"引擎"会引入方向参数化与状态注入,复杂度高于收益。WP-52 实现插件侧校验时按嵌入协议 §五逐条对映本包计数键即可保证语义一致。
4. **登记**:WP-56 回填 D-API 时,以本节为 Q4 定案文本来源。

## 二、实现期定案(供 WP-56 回填 D-API 时的核对清单)

1. **D-API-77 构造参数面落地形态**:全部参数在 `createEmbedSession(options)` 单点解析(`resolveEmbedSessionOptions`)。`handshakeTimeoutMs` clamp 3000–30000(默认 10000);`heightChangedMaxPerSecond` clamp 1–120(默认 30);`controlMessageMaxPerSecond` clamp 1–120(默认 10);`helloMaxRetries` clamp 0–10(默认 3);非整数/负数一律装配拒绝(`EmbedInvalidOptionError`)。`maxHeightPx` 默认 = 协议冻结常量,只可收紧,`> MAX_EMBED_HEIGHT_PX` **拒绝装配**(不 clamp,与 D-API-77 "超上限拒绝装配"逐字一致)。
2. **`helloMaxRetries` 的宿主侧语义**:该参数是插件侧重试预算(§4.3);宿主侧不消费其值发起任何重试——握手完成后再收 hello 一律按状态违规丢弃+计数(§4.5,`state-hello-after-ready`)。选项保留在构造面仅为参数面完整性(react-wrapper 薄封装透传、宿主诊断面板可读 `getResolvedParameters()`)。
3. **supportedVersions fail-closed**:宿主声明支持的每个版本必须在版本→Schema 注册表有对应版本 Schema(冻结期只有 v1),否则装配拒绝——宿主不得声明自己无法校验的版本(N-1 窗口开启时随 protocol 新 Schema 一起注册)。
4. **违规计数键命名**:以规则编号为前缀(`v1-origin-mismatch` … `v10-rate-limit`)+ `state-hello-after-ready`(§4.5 状态违规)+ `unavailable-drop`(不可用后迟到消息)。每次递增伴随 `violation-counters-changed` 事件,快照全键稳定(未命中补 0)——这是 V-12"宿主本地面"的可读出形态,不向对端反馈任何内容。
5. **入站校验顺序**(未在契约冻结,实现定案):不可用后迟到消息 → V-1/V-1'(含非 opaque 的窗口绑定复核,失败计 `v1p-source-mismatch`)→ V-2(字节上限在 JSON.parse 前;非字符串/非对象/解析失败计 `v2-non-json`,超限计 `v2-oversized`)→ V-3 → V-4 → V-5 → V-6 → 状态机分发(V-7 → V-8 → V-10)。
6. **宿主 API 误用 = 同步类型化错误,不属于 V-12 反馈面**:会话不可用后调用 `sendThemeChanged` 等控制面方法抛 `EmbedUnavailableError`(§4.5 停止投递);未授予能力抛 `EmbedCapabilityNotGrantedError`(§4.4 宿主发送义务);握手未完成调 `deliverTokenViaPort` 抛 `EmbedPortDeliveryError`(port 转移为必需前置)。V-12 约束的是 **postMessage 通道对端反馈**,入站违规永远静默丢弃+计数。
7. **V-10 出站自限语义**:宿主自身发送(theme_changed/language_changed)受 `controlMessageMaxPerSecond` 约束,超限**静默丢弃+计数并返回 false**(seq 不消费;插件侧跳号可接受,V-7)。
8. **重载语义(§4.5)**:`reload()` 生成新 esid、旧值立即作废(仅当前值全等,V-5 自动拒绝旧值)、对端 seq 高水位与能力授予清零、port 关闭复位、状态回 `idle`;`embed-reload-initiated` 事件携带新 esid 与新 iframe src(react-wrapper 的 handle 会同步更新 iframe.src;原生用法宿主自行重建 iframe 并等 load)。重载后的 token 重签由宿主自理(旧 token 因会话绑定不匹配自然失效,嵌入协议 §6.2)。
9. **iframe URL fragment 纪律(硬门槛的机械执行)**:`buildIframeSrc()` 是 fragment 唯一产生点(`#esid=<esid>`);构造选项 `pluginUrl` 携带 fragment 即装配拒绝。
10. **opaque 路径(V-1')**:opaque 模式下完全忽略 `event.origin`("null" 不作信任信号),仅接受 `event.source === iframe.contentWindow`(经 `attachIframe` 实时读取 contentWindow——iframe 重载后新文档窗口自动获得正确绑定);iframe 未挂接 = fail-closed 拒绝。非 opaque 模式除 origin 全等外**复核 source 绑定**(V-5 窗口对应关系),失败计 `v1p-source-mismatch`。
11. **host-mock dev 端点 CORS 姿态**:plugin-dev 的 dev 替身端点(`/host-api/*`)只服务同源调用,不回显 ACAO——引导配置(token 载体)不对其他 origin 开放;跨来源插件 URL 的引导配置取回由其自身后端承担(生产语义)。compose demo-override 无需增补:模拟页/桩页同在已登记的 `http://localhost:5173` origin,且插件 URL 可配置、模拟页不依赖具体插件端口(独立来源端口编排归 WP-52/55)。

## 四、移交 WP-52 的 wire 形态(通道级新信息,正式插件侧需按此对接)

1. **宿主→插件的 EmbedMessage 到达形态**:`iframe.contentWindow.postMessage(EmbedMessage对象, targetOrigin)`(结构化对象,非 JSON 字符串);非 opaque 时 targetOrigin 恒为宿主声明的 `pluginOrigin`,opaque 时 `"*"`。
2. **port 转移消息(V-13 前置)**:`contentWindow.postMessage(null, targetOrigin, [port2])`——data 恒为 `null`(零载荷,不携带凭证与绑定值),port 在 `event.ports[0]`。
3. **port 凭证信封**:`port1.postMessage({ kind: "stackmaster:embed-credential", credential: <token字符串> })`;kind 常量导出为 `EMBED_PORT_CREDENTIAL_KIND`。port 转移后,宿主的控制面消息(theme_changed / language_changed / 后续 ready 幂等重发)**也改走 port**(§4.2 控制面强化),信封仍为 EmbedMessage 六字段。
4. **宿主→opaque 插件的 token 交付前提**:插件先完成握手(ready 收到)才可能有 port 转移;通道 a(引导配置)与通道 b(port)可并存,WP-52 的 create-session 优先消费引导配置中的 token。
5. **桩页参考实现**:`stub-plugin.js` 的消息监听(兼容字符串/对象两种到达形态 + port 转移识别)可作为 WP-52 接收面的行为参考,但正式实现必须按嵌入协议 §五完整执行 V-1'/V-5/V-7/V-8。
