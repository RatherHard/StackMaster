**环境口径登记(本机 Chromium 出帧模型,非产品缺陷)**:Playwright/Chromium(Windows 本机)对跨源 iframe(OOPIF)按需出帧——帧在加载后产出一帧即停,须由交互(iframe 内点击)再次驱动;height_changed 的 rAF 合流管道因此「首帧排队、交互后释放」。诊断过程(一次性探针脚本,诊断后已删除):帧内 rAF 计数器实测「加载后恰一帧、交互即恢复」;真实浏览器(人工操作)不受此影响——WP-52 宿主模拟页人工走查与 WP-55 矩阵交互断言均为旁证。该模型同时解释 session.spec.ts 文件头登记的 lit-virtualizer 真实浏览器行渲染缺陷(虚拟化布局依赖渲染帧)。embed spec 的对策 = 先驱动一次 iframe 内交互再断言 height_changed(用例内注记)。

**注入面说明(宿主 / 插件两侧)**:宿主方向注入 = 宿主模拟页新增诊断面板(联调面,`host-mock/index.html` + `host-mock.js`:`host-mock-inject-target` / `host-mock-inject-scenario` / `host-mock-inject-button`),向宿主窗口自投递(不受信来源)或经 `iframe.contentWindow.postMessage` 向插件投递伪造控制消息(source === window.parent 且 origin 为钉住值,恰好穿过 V-1'/V-1 后命中 V-5/V-6/V-7/V-8);插件方向注入 = E2E 以 Playwright 跨源帧求值在插件上下文发 `window.parent.postMessage`(「受入侵插件面」威胁模型)。同批增补能力授予勾选(`host-mock-cap-auto-resize` / `host-mock-cap-theme` / `host-mock-cap-language`),映射 `createEmbedSession` 的 `grantableCapabilities`(§4.4 宿主授予面)。
