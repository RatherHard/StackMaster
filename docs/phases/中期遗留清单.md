### P2-1 · 遗留 14 —— terminal 三面的 axe color-contrast 自动判定覆盖度倒挂(「薄绿」)
- **原§六#14** · **状态 = 仍开放(证据强度项)** · **归属 = 证据强化项(待派单)**
- **实测(逐面读归档 JSON,字段 = `colorContrastCheckedNodes` 与 `incomplete[].count`)**:

| 扫描面 | violations | 自动判定通过 | 无法判定 |
|---|---|---|---|
| plugin-iframe light / dark × registers / stack(4 面) | 0 | **132** | 7 |
| plugin-dev-shell light | 0 | **146** | 7 |
| plugin-degraded light | 0 | 2 | 0 |
| **plugin-iframe terminal × registers / stack(2 面)** | 0 | **7** | **132** |
| **plugin-dev-shell terminal** | 0 | **19** | **134** |

- **判据**:九面 `violations = 0` 本身为真,但**不能据此认为 terminal 预设的对比度已被验证** —— 该预设下 axe 只能自动判定 7 / 19 个节点。light / dark 是 132/7 的**正向覆盖**,terminal 是 7/132 的**倒挂** ⇒ 同一句「零 violations」在两类面上证据强度**不可等同**。
- **性质**:**非 M3 引入**,亦**非产品缺陷判定** —— 是**证据强度**问题。上游 `color-contrast` 规则在存在**半透明覆盖层**时无法计算合成对比度(terminal 的效果面:扫描线 `opacity ≤ 0.06`),此为 axe 的已知判定边界。
- **候选修法**:① 对 terminal 面做**关闭效果层后的对照组扫描**;② 引入**脚本化对比度核算**(按 token 前景 × 合成背景实算 WCAG 比值)补齐 `incomplete` 面;③ 归档汇总**强制分列**「自动判定通过 / 无法判定」两栏。
- **纪律**:**不得以沉默结案**。

## 五、P3 契约面与覆盖缺口(6 项)

### P3-1 · 遗留 24 —— 镜像表跨包 / 跨源漂移无机检(建议合并立项)
- **原§六#24** · **状态 = 仍开放** · **归属 = 待派单** · **建议合并为一个「镜像表静态互证机检」WP**
- **事实**:`protocol` 动作参数名表 ↔ `challenge-schema` `AUTHOR_BLOCK_ACTION_ARGS` **有意重复**(叶子包不依赖 protocol,依赖纪律 5.5 要求如此),现有断言**只在 challenge-schema 包内**(键集 ≡ 12 动作、并集 ≡ 参数名全集、必填 ⊆ 允许),**没有任何检查**把这张表与 protocol 的**真实**参数名表对比 ⇒ 任一侧改名 / 增删参数时另一侧**不会红**(服务端入站重校验只兜**运行期**,兜不住**静态漂移**)。
- **同族(合并理由)**:WP-78 转来的「**`docs/contracts/版本策略.md` 契约类目表 ↔ `version.ts` 常量漂移无机检**」为**同一族缺陷** —— **文档 / 镜像表与权威源之间无静态互证**。

### P2-附-1 · 遗留 33 —— 门禁对「窗口高度可读性 / 溢出列拖拽有效性」零覆盖
- **原§六#33** · **状态 = 仍开放** · **归属 = 待派单(建议并入 WP-88 几何链复核)** · **来源 = 主控验收 + 交互修复轮真机取证**
- **事实**:266px 下限抬升后,**单元 `895 passed`、typecheck、`scan:public`、`lint:deps` 全部 exit 0**,而**真机 E2E 抓出两条失效**(窗高拖拽只兑现 7.5px;三类拖拽落点不送达)。此前窗口被压到 **146px** 时,axe **9/9 面 violations = 0**、全套 E2E 亦绿。**没有任何门禁断言「窗口至少显示 N 行字节」** —— 门禁只断言下限**常量的推导式**(`MIN_ROW_HEIGHT_PX = ceil(chrome + N × 行单位)`),**不断言渲染结果**。
- **定性**:证据强度缺口(非功能缺失)。**几何类缺陷系统性不被现有门禁覆盖**:jsdom 无布局引擎(vm-ui 侧只能做结构断言)、axe 只看无障碍与对比度、而全量 E2E 未纳入中期验收必跑面。
- **下一步动作**:在 E2E 增加一条**几何护栏**用例 —— 断言「每个窗口高度 ≥ `MIN_ROW_HEIGHT_PX`」且「字节视图可见数据行 ≥ N」;不得只断言常量算式。
- **触发条件**:任何改动**面板 chrome / 行高 / 下限常量 / 列弹性语义**时(改动者必须重跑真机几何)。

### P2-附-2 · 遗留 36 —— `MIN_COLUMN_WIDTH` 的「十六进制行不折行」前提在现有三档列宽下不成立
- **原§六#36** · **状态 = 仍开放** · **归属 = 待派单(建议优先于其他 P2)** · **来源 = 窗口压扁修复轮新发现**
- **事实**:宽度下限的推导前提是「十六进制行不折行的最小可读宽度 = `58ch × 7.8px` = **452.4px**」;但**字节视图自身还带一个 `14rem`(224px)侧栏**(`src/workspace/byte-tab.ts` 的 `grid-template-columns: minmax(0,1fr) 14rem`)⇒ 在 452.4px 的列里,字节视图实际只有 **≈220px**,行**必然折行**(真机实测:工具区 328.3、列头行 84.2、数据行 259.6)。**要免折行需 ≈766px 视图宽 ⇒ 列宽 ≈1000px。**
- **定性**:**既有不变量(documented invariant)的前提失效** —— 任何人依据 `MIN_COLUMN_WIDTH` 的推导表推断「该列宽下字节行不折行」都会得出**错误结论**。形态上合 P0 判据(「不处置会产生错误结论」),但影响面是**呈现**而非安全/证据,故定 P2。
- **下一步动作(三选一,须先定案再改阈值)**:
  1. **收窄 / 可折叠**该 14rem 侧栏;
  2. 把列宽下限抬到「侧栏 + 免折行视图宽」(≈1000px),**并重算 P0 / P1 / P2 三档阈值**;
  3. **明文改述**该推导的适用条件(承认现有三档列宽不足以免折行)。
- **触发条件**:任何依据 `MIN_COLUMN_WIDTH` 推导表做结论时(尤其排版 / 宽度相关决策)。

### P3-附-1 · 遗留 34 —— 拖拽落点出视口即不可达(缺「拖拽中自动滚动」)
- **原§六#34** · **状态 = 仍开放** · **归属 = 待派单(建议并入 WP-88)** · **来源 = 交互修复轮真机取证**
- **事实**:266px 下限使工作区高于宿主视口(1440×900 下页面高 **1322px**)后,拖拽终点若落在视口外,**浏览器对视口外坐标不命中页面内容**(逐事件取证:`event.target === html`,组件 shadow root 收不到)⇒ 组件收不到 `pointermove` / `pointerup` ⇒ **拖拽不生效且不收尾**。E2E 夹具已改为「拖拽前把**起点与终点一起**滚进视口」。
- **定性**:真实用户同样**必须先滚动再拖**(所以不是产品缺陷,而是**能力边界**);缺的是**拖拽过程中的自动滚动**(把窗口拖向视口外目标时自动滚屏)。**须与既有口径对齐后再决定是否实现。**
- **下一步动作**:定案是否实现拖拽中自动滚动;若实现,须同时给出「自动滚动**不改变落点语义**」的机检(落点仍按目标元素的上半 / 下半判定)。
- **触发条件**:用户反馈「拖不到下面的窗口」时。

### P3-附-2 · 遗留 37 —— 宿主未给工作区定高 ⇒ 条带自身纵向滚动在两种已发布形态下都不会出现
- **原§六#37** · **状态 = 仍开放** · **归属 = 待定案(改动落在 `packages/web-component`,跨包)** · **来源 = 窗口压扁修复轮形态复核**
- **事实**:两种已发布形态宿主的条带高度都是**内容驱动**(`clientHeight ≡ scrollHeight`):开发壳 `sm-workspace` 为 auto 高;嵌入形态插件**只上报内容高**、宿主 `MAX_EMBED_HEIGHT_PX = 960` 钳制 ⇒ 溢出**上浮到文档层滚动**。实测注入 `:host { block-size: 660px }` 后条带才 `vScroll = true`(`clientHeight 465` / `scrollHeight 1160`)。
- **定性**:产品面「空间不足时**列纵向滚动优先于压缩**」的口径**以「宿主给工作区定高」为前提**,而**两种已发布形态都不满足该前提** ⇒ **口径与现状之间有一条未收口的缝**,须**显式定案**(不是默认忽略)。
- **下一步动作(二选一)**:
  1. 让 `pwn-memory-vm` 在工作区层给 `block-size: 100%`(跨包改动,使条带成为滚动容器);
  2. **改述口径**为「溢出由宿主 / 文档层滚动承载」,并同步 `docs/user/界面帮助手册.html`。
- **触发条件**:宿主侧要求工作区**自身**滚动(而非页面滚动)时。

### P4-附 · 遗留 35 —— 开发壳 `.tab-area` 无高度上限,工作区整体溢出视口
- **原§六#35** · **状态 = 仍开放** · **归属 = 待派单(开发壳小项)** · **来源 = 交互修复轮真机取证**
- **事实**:开发壳 `.plugin-dev-shell .tab-area` 只有 `min-block-size: 32rem`、**没有高度上限** ⇒ 工作区被内容撑到 **1163px**、页面 **1346px**;**嵌入拓扑里由 `pwn-memory-vm` 定高**,故这只在 dev 壳可见。**「宿主定高时条带内滚动」的产品口径成立,但 dev 壳不满足「宿主定高」前提** —— 这也是两条 E2E 必须滚动才能拖的根因。
- **定性**:开发壳 / 宿主约束问题(非产品缺陷)。
- **下一步动作**:给 dev 壳 `.tab-area` 一个视口相关定高(如 `block-size: calc(100dvh - <头部高度>)`),使开发壳能复现嵌入形态的**定高前提**。
- **触发条件**:任何依赖「条带自身滚动」的联调或 E2E(当前两条用例已受影响)。
