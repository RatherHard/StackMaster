## 二、部署拓扑(compose 单机公网)

### 2.1 形态

单台主机 + Docker Compose,`deps.yaml` 与 `app.yaml` **合并为同一 compose 项目**(既有用法,`compose/app.yaml` 文件头 30-33 行):

```text
公网客户端 / 宿主平台(域 A)
   │  HTTPS(443)
   ▼
反向代理(终止 TLS;ACME 证书)          ← 待执行形态(O-MP-5)
   │  HTTP(回环 / 内部网络)
   ▼
session-api(13000:3000)──spawn──▶ vm-worker(按会话一次性子进程,ADR-3)
   │                    ▲
   │                    │ 经 PG / MinIO 单向解耦(D-API-83)
   ▼                    │
PostgreSQL 16(15432)   verifier(13100:3100;独立网络域 verifier-net)
Redis 7(16379)          └ MinIO(19000 / 控制台 19001)
MinIO(19000 / 19001)
```

- `vm-worker` **不是常驻服务**:由编排器按会话 spawn(单会话单进程);compose 中的 `vm-worker` 服务是一次性 linux 二进制冒烟(`profiles: ["smoke"]`,不参与 `up --wait`,D-API-64);
- 信任域边界(5.2 / 5.3):session-api = 信任域 2,vm-worker = 信任域 3,verifier = 信任域 4(独占 `verifier-net`,`session-api` **不入该网络**);
- Redis 只存可重建、带 TTL 状态(`--save "" --appendonly no`),不作权威(ADR-4)。

### 2.2 端口清单(与 compose 定义逐条对应)

| 宿主端口 | 容器端口 | 服务 | 用途 | 是否必须公网暴露 |
|---|---|---|---|---|
| 13000 | 3000 | session-api | 业务 REST + 认证 WSS + `/healthz` `/readyz` `/metrics` | 业务面必须可达;**运维端点不得裸暴露**(第五章) |
| 13100 | 3100 | verifier | 裁决服务(内部)+ `/healthz` `/metrics` | **不必要**(裁决由 verifier 主动认领队列,不经公网入口) |
| 15432 | 5432 | PostgreSQL | 唯一权威存储(5.7) | **不必要**(仅 compose 网络内) |
| 16379 | 6379 | Redis | 可重建状态 | **不必要** |
| 19000 | 9000 | MinIO | 私有判题包 / 公开描述包 / 审计归档对象 | **不必要**(仅内部;verifier 最小授权角色直连) |
| 19001 | 9001 | MinIO 控制台 | 运维图形面 | **绝不公网暴露** |
| 443(待接入) | — | 反向代理 | 试用环境唯一公网入口 | 是(O-MP-5 阻塞) |

> **现状登记**:上表 13000 / 13100 / 15432 / 16379 / 19000 / 19001 均按 `dev` 形态**发布到宿主 `0.0.0.0`**(`compose/*.yaml` 的 `ports:` 现状),即按现状部署会把这些端口直接挂上公网。试用环境前必须按第九章的收敛动作逐条收敛 —— 该发布面是 k6 采样(D-API-73)、compose 机检与运维探活所依赖的 **dev / CI 形态**,不是试用 / 生产形态(D-API-104 现状登记)。

### 2.3 依赖与执行序(无环)

```text
postgres(healthy) → db-roles-init(healthy) → session-api(healthy)
  → session-api-db-init(exit 0) → verifier-db-init(exit 0) → verifier
```

- `db-roles-init` 的**健康**语义 = 两个角色在场且非 superuser / 非 bypassrls(强于 `service_completed_successfully`);
- 迁移 007(`CREATE POLICY ... TO session_app / TO verifier`)要求角色先存在,故 `session-api` 以 `db-roles-init: service_healthy` 为迁移前置;
- 两个角色治理 init 串行(`session-api-db-init` 先于 `verifier-db-init`):二者写同一批 PG 目录行,并发会偶发 `ERROR: tuple concurrently updated`;
- **迁移自动执行**:session-api 启动序列自带 `runMigrations`,失败即拒绝启动(fail-closed),**无需手工迁移步骤**。

## 四、最小授权角色连线(生产连线义务的兑现)

### 4.1 连线口径

| 面 | 生产 / 试用连线要求 | 角色来源 | 依据 |
|---|---|---|---|
| 应用连接(session-api) | `SESSION_API_POSTGRES_URL` **必须使用最小授权角色 `session_app`**,不得使用表属主 | `compose/db-roles-init.sql`(创建唯一来源;口令唯一来源亦在此文件) | D-API-93(`:820`)、D-API-101(`:932`) |
| 应用连接(verifier) | `VERIFIER_POSTGRES_URL` 使用独立最小授权角色 `verifier`(与 session-api **不共享凭证**) | 同上 | D-API-87、D-API-101 |
| 迁移执行 | 由**专用迁移角色(表属主)**执行;表属主的隐含权利不受 `REVOKE` 影响 | compose 管理面凭证(dev 为 `stackmaster`) | D-API-93(`:820`) |
| MinIO | verifier 经最小授权角色只读 `private-bundles/*` / `public-descriptors`(策略文件 `compose/verifier-minio-policy.json`) | `compose/verifier-minio-init.sh` | D-API-87 |
| **RLS 生效前提** | 两个角色必须是**非 superuser / 非 bypassrls**(`db-roles-init.sql` 末尾只读不变量断言:违者以确定性失败暴露) | 同上 | D-API-101 |

**为什么这条连线是生产义务而不是可选项**:dev compose 拓扑的应用连接走管理面凭证(超级用户,**RLS 旁路**)⇒ 行级租户强制在 dev 形态下**不生效**;生产 / 试用连线到 `session_app` 后 RLS 才在该形态下强制生效(D-API-101 双层结构闸的第二层)。

### 4.2 dev 拓扑的降级形态(**生产前必须消除的差异**)

`compose/app.yaml`(`:198-202`)已如实登记:

> dev 拓扑的应用连接仍走管理面凭证属角色治理降级(如实登记,与 verifier host 形态同纪律);生产连线义务(应用经本角色连接)随部署面执行。

即:**dev / CI 拓扑 = 角色在场 + 授权面齐备,但应用仍以管理面凭证连接**。该差异在三处参数上体现,试用环境部署前**必须逐条消除**:

| 键 | dev 形态(降级) | 试用 / 生产形态(必须) |
|---|---|---|
| `SESSION_API_POSTGRES_URL` | 用户 = 管理面(表属主 / 超级用户) | 用户 = `session_app`(最小授权,RLS 强制) |
| `VERIFIER_POSTGRES_URL` | 同族降级 | 用户 = `verifier` |
| RLS 生效性 | **旁路**(对 superuser 不成立) | **强制**(ENABLE + FORCE 对非旁路角色成立) |

> 判定方法(试用前自查项,可复跑):以应用连接串连库后 `SELECT current_user, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user;` —— 试用形态下 `current_user` 必须为 `session_app` 且两个布尔值均为 `false`。**该查询的取值属运维面,不入本文。**

## 五、运维端点暴露面(`/metrics` `/healthz` `/readyz`)——按 D-API-104 择一

### 5.1 三选项与选择

D-API-104 成文三选项(原文口径见 `docs/develop/权威API语义规约.md:981`):

| 选项 | 形态 | 在本试用拓扑下 |
|---|---|---|
| ① 内网段形态(**D-API-104 的基线推荐**) | 应用端口不发布到公网宿主,`/metrics` 仅内网可达(Prom 抓取器与探针同内网) | **不可直接采用**:单机 compose 公网形态下没有独立内网段;应用端口必须发布到宿主才能被反代访问 ⇒ 「不发布」与「公网可用」不相容 |
| ② **反代准入形态** ✅ **本试用环境择此** | 公网入口反代对 `/metrics`(及 `/healthz` `/readyz`)路径做准入控制(allowlist / 基本认证 / 来源 IP 白名单),**应用侧零改动** | 采用;与单机公网拓扑相容,零应用改动,准入面集中在一处 |
| ③ 独立端口形态 | 管理面端口单独暴露指标族(需反代改写或应用侧多监听器;后者 = 端点语义外的装配演进) | 不采用:多监听器属本阶段外的装配演进,收益不抵复杂度 |

**选择理由(②反代准入)**:单机公网试用环境下,应用端口必须经反代暴露业务面 ⇒ 运维端点天然与业务同端口(D-API-104 现状),因此**准入只能在反代层做**;该选项**不动 `METRIC_FAMILIES`、不动端点语义、不动白名单机检**(D-API-104「零代码改动为基线」),且与 D-API-70「暴露面收敛是部署面配置事项,不是端点语义变更」一致。

### 5.2 反代准入的落地口径(待执行形态)

- 公网入口**只暴露反代 443**;`session-api` / `verifier` 的宿主发布面收敛为**回环绑定或仅反代可达**(compose `ports:` 现状为 `0.0.0.0`,收敛动作见第九章);
- 反代对 `/metrics`、`/healthz`、`/readyz` 三条路径**独立准入**(来源 IP 白名单 / 基本认证 / allowlist 三选一或叠加);业务路径不施加该准入;
- **不得公网裸暴露**:三条端点均为**未认证 GET**(D-API-70 / D-API-89 纪律),裸暴露等于把指标族与服务健康形态无凭证地交给任何公网调用方;
- 指标载荷本身仍是**零秘密零标识符**(聚合数值 + 有界枚举;机检 `assertMetricsTextDiscipline`,D-API-71)⇒ 本约束的动机是**部署面收敛**,不是载荷泄密补救;两者不互相替代;
- `/readyz` 的探针为 PG / Redis / MinIO(D-API-34),准入不影响容器内 healthcheck(`compose/app.yaml` 的 healthcheck 走**容器内** `127.0.0.1`,`127.0.0.1` 属白名单内网口径,必须留在准入允许面内)。

## 六、环境变量与秘密注入

### 6.1 `.env` 形态说明

- session-api 配置走 `SESSION_API_*` 环境变量,三道闸校验(必备键缺失 / 未知保留键 / 取值非法,任一不过即拒绝启动,D-API-9);错误消息只含**字段名与原因**,绝不回显取值;
- compose 形态的键值集中在 `compose/app.yaml`(**dev / CI 合成值**),宿主进程形态在 `compose/integration.env`;依赖服务模板 = `compose/.env.example`(复制为 `.env` 使用);
- **严禁提交 `.env`**:`.env` 属秘密载体,永不入 git(《CLAUDE.md》提交纪律;秘密零驻留 ZR-B 族纪律)。试用环境建议形态 = **宿主受控目录中的 `.env`(权限收紧)+ compose `env_file`** 或宿主 secret 机制,二者都不产出入库文件;
- `compose/app.yaml` 与 `compose/integration.env` 中的凭据 / 密钥**全部是本地 dev / CI 专用合成值,严禁用于任何真实环境**(文件头原文);试用环境**必须全部更换**。

## 八、回滚步骤

| 场景 | 命令 | 数据后果 |
|---|---|---|
| **保留数据的停机回滚**(推荐) | `docker compose -f apps/session-api/compose/deps.yaml -f apps/session-api/compose/app.yaml down` | 停止并删除容器 / 网络;**数据卷 `pgdata` / `miniodata` 保留** |
| **清场式回滚**(既有脚本,**含数据卷**) | `pnpm --filter @stackmaster/session-api compose:app:down`(= `... down -v`) | **`-v` 删除数据卷:PostgreSQL 权威数据、快照密文、MinIO 对象(含私有判题包与审计归档)全部丢失且不可恢复** |
| 仅依赖服务清场 | `pnpm --filter @stackmaster/session-api compose:deps:down`(= `... down`,**不带 `-v`**) | 保留数据卷 |
| 回滚到上一版本镜像 | 切回上一版本工作树后 `compose:app:up`(重建镜像) | 数据卷不动;**版本语义见 `docs/contracts/版本策略.md`** |

**数据卷处置注意(逐条)**:

1. `compose:app:down` **带 `-v`** ⇒ 试用期禁止无条件使用;试用期清场前必须先导出审计归档与数据库备份;
2. 快照列存的是 **AES-256-GCM 密文信封**(明文永不落库,D-API-21)⇒ 备份即密文,但**密钥丢失 = 数据不可恢复**;`SESSION_API_SNAPSHOT_ENCRYPTION_KEY` 的备份与轮换纪律属运维面;
3. 迁移**前向不可逆**:回滚镜像到旧版本时,新版本已应用的迁移不回退(迁移 runner 只前进);版本回退的兼容窗口见 `docs/contracts/版本策略.md`(N-1 兼容窗口);
4. 审计账 `audit_log` 与动作账 `action_log` 为 **append-only**(库层触发器禁 UPDATE / DELETE / TRUNCATE,`migrations/003_action_log.sql`;应用角色侧 REVOKE UPDATE/DELETE 为第二层,D-API-22 / 93)⇒ **回滚不提供"删行修正"路径**,任何账面条目修正只能以新增批次归档表达;
5. 端口冲突清场:13000 / 13100 / 15432 / 16379 / 19000 / 19001 为固定发布,先 `compose:app:down` 或 `compose:deps:down` 清场。
