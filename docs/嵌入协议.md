## 一、范围与冻结清单

本 WP 冻结:

1. `EmbedMessage` 消息信封:六字段 + 5 种消息类型的判别联合(`schema/embed-message.schema.json`);
2. `EmbedTokenClaims` 绑定字段集合:七字段(`schema/embed-token-claims.schema.json`);
3. handshake 流程与全部降级路径(本文 §四,时序图覆盖常规路径、opaque origin 路径、版本协商失败、能力降级、超时与 iframe 重载);
4. 接收端校验规则清单 V-1 – V-13(本文 §五,逐条可测;13.3 场景 → 规则映射见 §5.1);
5. 机检产物:上述两个 JSON Schema、`schema/classification.json` 字段分类清单、`test/fixtures/embed-message/**`(28 个)与 `test/fixtures/embed-token-claims/**`(7 个)——后者是 WP-6 golden fixture 的增量来源。

**不归本 WP**(边界声明):

- **embed-runtime 宿主侧 SDK 与插件 iframe 实现归阶段五**(8.2 / 阶段一任务分解 §三):本 WP 只冻结消息契约与校验规则,不写任何宿主侧 / 插件侧实现代码;
- **embed token 的签发、下发与校验实现归阶段五**;本文 §六只冻结字段集合并给出生命周期设计;
- **浏览器 ↔ 编排器的 WSS / HTTP 传输信封归阶段二 / 三**(WP-2 语义文档 §一移交项的收口):本协议是 postMessage 通道的嵌入协议,不是动作协议的传输帧;`ActionRequest` / `ActionResponse` 不经 postMessage 承载;
- 会话动作、公开投影、错误契约的内容边界归 WP-2 / WP-3,本协议对其零重复、零修改。

**与 VM 解耦**(与 WP-2 同纪律):嵌入协议不感知地址位宽、寄存器、区域布局或任何 VM 语义;它甚至不感知题目内容——宿主与插件之间的全部业务数据(投影、动作、错误)都走浏览器 ↔ 编排器的认证通道(6.2)。

## 二、信封与字段分类

### 2.1 `EmbedMessage`(双向,整体 `BOUNDARY`)

| 字段 | 类型(冻结) | 语义与规则 |
|---|---|---|
| `protocolVersion` | `const 1` | 只接受接收端支持的版本;N-1 窗口由接收端按版本双受理(§五 V-3) |
| `type` | 5 值封闭枚举 | `hello` / `ready` / `height_changed` / `theme_changed` / `language_changed`;方向由类型唯一决定(§三),未知类型即 Schema 拒绝(V-4) |
| `sessionId` | 不透明字符串(22–128,`^[A-Za-z0-9_-]+$`) | **嵌入会话标识**:宿主以 CSPRNG 生成(≥ 128 bit,base64url 编码恰 22 字符——`minLength: 22` 把熵下限冻结进契约层,短于下限的值在 Schema 校验即拒绝)、经 iframe URL fragment 一次性下发(§四);兼任 opaque origin 场景的握手认证值——不可预测 + 一次性,iframe 重载即轮换(§4.2 / §4.5) |
| `seq` | 整数 ≥ 1 | 发送方会话内严格递增序号(允许跳号);接收端维护对端高水位,`seq ≤` 高水位即重复 / 过期,丢弃(V-7) |
| `requestId` | 不透明字符串(可选) | 请求-响应对的关联 ID;本版本无强制使用该字段的消息对,字段为 8.2 最低字段清单的组成部分 |
| `payload` | 按 `type` 判别的 strictObject | 五种载荷 Schema 见 §三;未知字段在契约层拒绝 |

两侧发送内容都落在选手控制域内(9.2:**浏览器完全不可信**涵盖宿主页面本身),故整体分类 `BOUNDARY`:接收端对一切入站消息按同一契约**重新校验**(5.6),不信任发送方类型标注。strictObject → `additionalProperties: false`:伪造的信封字段(如伪造成绩、伪成功标志)在契约层直接拒绝——`test/fixtures/embed-message/invalid/06-unknown-envelope-field-tamper.json` 即该篡改形态的机检红灯样例。

判别联合的跨字段耦合(`type` ↔ `payload`)由结构表达(每个分支携带 `type` 常量与对应 payload Schema),不依赖 refinement,保证 TS(Zod)与 Rust(serde + schemars)校验结论一致。

### 2.2 `EmbedTokenClaims`(短期凭证载荷,整体 `BOUNDARY`)

| 字段 | 类型(冻结) | 语义与规则 |
|---|---|---|
| `tenantId` | 不透明字符串 | 五要素(9.2):租户绑定;服务端校验时与 host 凭证的租户契约比对,不采信自报(WP-1 §1.2 WP-5 行) |
| `userId` | 不透明字符串 | 五要素:用户绑定;create-session 从认证上下文重新派生(6.2 第 1 条) |
| `challengeId` | 不透明字符串 | 题目身份:版本号脱离题目 ID 无意义(与 challenge-schema XS-ID-CORR 的共享身份对同构) |
| `challengeVersion` | `X.Y.Z` 语义化版本 | 五要素:题目版本绑定;格式与 challenge-schema 的 `challengeContentVersion` 同一冻结字面量 |
| `embedSessionId` | 不透明字符串 | 五要素:iframe 会话绑定;值必须等于该次嵌入的 `EmbedMessage.sessionId`,重载轮换后旧 token 不再匹配(V-5) |
| `jti` | 不透明字符串 | token 实例标识:单用途 / 有限次数语义与吊销键(WP-1 §二 Redis `token:{jti}`,域 2,带 TTL) |
| `expiresAt` | 整数(epoch 秒,UTC) | 五要素:过期时间;签发 TTL ≤ `MAX_EMBED_TOKEN_TTL_SECONDS`(7 天外圈护栏,具体 TTL 为阶段五运维参数) |

字段集合 = 计划书 9.2 五要素(租户、用户、题目版本、iframe 会话、过期时间)+ `challengeId`(身份对补全)+ `jti`(§二存储表已 sanction 的吊销键)。claims 对持票玩家本身无秘密性——租户 / 用户 / 题目上下文皆为其可见会话信息(WP-1 §二"短期会话凭证"行:`BOUNDARY`、浏览器短期持有);防伪造靠签名(密钥仅在域 2),防重放靠 `jti` 一次性 / 限次 + 过期时间 + 会话绑定。浏览器对 token **保持不透明**:不解析、不校验、不在会话期外留存。签名与序列化载体(JWT / PASETO / 自有格式)是阶段五实现决策,本 Schema 冻结的是签名前 claims 载荷的字段集合。

### 2.3 分类标签与机检

- 两个根 Schema 均携带 `x-sm-class: boundary`,字段分类落盘在 `schema/classification.json`(v1.9 增补,机检条目引用 WP-1 §6.4);
- `embed-message` 是判别联合根(无顶层 `properties`),schema-drift 测试按"每个分支的属性键集 === fieldClasses 键集"断言;`embed-token-claims` 按常规对象根断言;
- **导出面纪律**:`EmbedMessage` 的解析器从包入口导出(信封消息的收发两侧都在浏览器,解析器必须在场);`EmbedTokenClaims` 的解析器**只**经 `@stackmaster/protocol/server-only` 子路径导出——浏览器对 token 不解析,claims 解析器仅供后端签发 / 校验消费,不给浏览器可达代码提供"解析 token 做条件渲染"的反模式入口;其 JSON Schema 落盘产物保持公开供跨语言机检(`x-sm-class` 仍为 `boundary`,分类与导出位置无关);
- postMessage 通道上不存在任何 SERVER_ONLY 类型的 sanctioned 路径——投影策略等配置对象进入该通道即违规(ZR-R1 / ZR-R3 覆盖);"Schema 存在不等于可下发"纪律原样适用。

## 三、消息类型(5 种,逐一冻结)

| 消息 | 方向 | payload(冻结) | 语义 | 接收端行为要点 |
|---|---|---|---|---|
| `hello` | 插件 → 宿主 | `supportedVersions`(整数 ≥ 1,1–8 项)、`capabilities`(能力枚举,≤ 3 项) | 握手起点:插件自 URL fragment 取得 `sessionId` 后发出,声明版本候选集与可选能力 | 宿主校验 V-1 / V-1' / V-5 后做版本协商与能力授予;握手完成后再收 `hello` 属状态违规,丢弃 + 计数 |
| `ready` | 宿主 → 插件 | `grantedCapabilities`(能力枚举,≤ 3 项)、`config`(`theme` + `language`) | 握手完成:授予能力子集并下发初始外观配置 | 插件校验 V-1' / V-5 / V-7 / V-8 后进入就绪;此后插件发送一律使用本消息 `event.origin` 钉住的明确 `targetOrigin`(§4.2) |
| `height_changed` | 插件 → 宿主 | `heightPx`(整数,1–100000) | 自适应高度上报;**仅当 `auto_resize` ∈ grantedCapabilities 时允许发送**(V-8) | 宿主据此调整 iframe 高度;未授予时收到即违规丢弃;宿主可按实现期节流策略进一步收紧 |
| `theme_changed` | 宿主 → 插件 | `theme`(`light` / `dark` / `auto`) | 运行中主题切换;**仅当 `theme` 已授予时允许发送**(V-8) | 插件重渲染主题;未授予时收到即违规丢弃 |
| `language_changed` | 宿主 → 插件 | `language`(BCP-47 规范语法子集,2–35 字符) | 运行中语言切换;**仅当 `language` 已授予时允许发送**(V-8) | 插件切换 UI 语言;未授予时收到即违规丢弃 |

- 能力枚举封闭:`theme` / `language` / `auto_resize`(基数与 `MAX_EMBED_CAPABILITIES` 一致);主题取值封闭:`light` / `dark` / `auto`(`auto` = 插件跟随自身 `prefers-color-scheme`);语言标签为 BCP-47 规范语法子集(不含私有用语法与祖传标签,模式在 TS / JSON Schema 两侧同串)。扩展任一枚举 = 协议版本演进;
- 版本协商规则(语义,非 Schema 面):宿主取 `hello.supportedVersions` 与宿主支持版本集交集的**最大值**;候选集顺序与重复不影响结论(max-wins),故 Schema 不约束有序性、TS 与 Rust 校验自然一致。交集为空 → 走 §4.3 失败路径;
- 本协议中不存在任何承载"结果 / 分数 / 通过状态"的消息类型或字段;`heightPx` 是唯一的数值业务字段,上限 100000(`MAX_EMBED_HEIGHT_PX`,防伪造巨型高度冲击宿主布局的外圈护栏)。

## 四、handshake 流程(时序图)

### 4.1 常规路径(独立来源 iframe,非 opaque origin)

```mermaid
sequenceDiagram
    participant HB as 宿主平台后端
    participant HP as 宿主页面(域 1)
    participant PI as 插件 iframe(独立来源)

    HP->>HP: 生成 embedSessionId(CSPRNG ≥128bit,一次性)
    HB->>HP: embed token(经宿主后端向 session-api 申请,§六;不进 URL query)
    HP->>PI: 创建 iframe(src = 插件 URL + "#esid=<embedSessionId>",sandbox 最小权限)
    PI->>PI: 加载完成,读取 location.fragment 中的 esid
    PI->>HP: postMessage hello {sessionId=esid, seq=1, supportedVersions, capabilities}(targetOrigin 规则见 V-11)
    HP->>HP: V-1(origin)/ V-1'(source = iframe.contentWindow)/ V-5(sessionId 知识证明)
    HP->>HP: 版本协商 = max(双方支持集交集)
    alt 交集非空
        HP->>PI: postMessage ready {sessionId, seq=1, grantedCapabilities ⊆ capabilities, config{theme, language}}(targetOrigin = 插件来源;opaque 插件走 §4.2)
        PI->>PI: V-1' / V-5 / V-7 / V-8 校验,钉住宿主 origin,进入就绪
        opt auto_resize ∈ grantedCapabilities
            PI->>HP: height_changed {heightPx}(此后按内容变化持续上报,宿主侧节流)
        end
        Note over HP,PI: 握手完成。此后一切业务数据(动作 / 投影 / 错误)走插件 ↔ session-api 的认证 HTTPS / WSS 通道(6.2),不经本通道
    else 交集为空
        Note over HP,PI: 宿主不回 ready → §4.3 版本协商失败路径
    end
```

要点:

- **embed token 不经本协议字段下发**(信封无 token 字段,冻结集合不容私加),也**禁止经 `targetOrigin: "*"` 的 postMessage 消息承载凭证或绑定值**(V-13):交付通道候选为 (a) 非 postMessage 通道(默认:宿主服务端把 token 注入插件引导配置),或 (b) 握手完成后经**已绑定端点**的 MessageChannel port 下发(此时 port 转移是该路径的必需前置,见 §4.2);无论哪种,禁止进入 URL query(8.1 不应把凭证放入 iframe URL;fragment 中只放 `embedSessionId` 这一无权限语义的会话标识,且不进浏览器历史之外的任何持久化);
- `hello` 阶段插件不知道宿主来源(跨浏览器不可靠地依赖 `ancestorOrigins`),允许 `targetOrigin: "*"`(接收面唯一为 `window.parent`,宿主侧 V-1 / V-5 / V-7 全量补偿);插件收到 `ready` 后即以 `event.origin` 钉住宿主来源,后续发送一律用明确 `targetOrigin`(V-11);
- 宿主侧对非 opaque 插件恒用明确 `targetOrigin`(插件来源是其自建的 iframe src,天然已知)。

### 4.2 opaque origin 路径(sandbox 无 `allow-same-origin`)

```mermaid
sequenceDiagram
    participant HP as 宿主页面
    participant PI as 插件 iframe(opaque origin,event.origin === "null")

    HP->>PI: 创建 iframe(sandbox 不含 allow-same-origin;URL fragment 携带一次性 esid)
    PI->>HP: hello {sessionId=esid, …}(event.origin = "null";宿主不得以 "null" 为信任信号)
    HP->>HP: 附加控制代替来源校验:V-1'(source === iframe.contentWindow)+ V-5(sessionId 知识证明)+ V-7(seq 防重放)
    HP->>PI: ready {…}(targetOrigin: "*";opaque 目标无法指定具体 origin)
    Note over HP,PI: "*" 不是信任控制——信任来自:仅真实嵌入方知道 esid(它生成并写入 fragment),仅插件读得到 fragment;source + sessionId + seq 三重绑定
    opt 控制面强化(v1 可选)/ 凭证或绑定值交付(必需)
        HP->>PI: 建立 MessageChannel,转移 port
        Note over HP,PI: 握手后消息改走 port:端点经绑定,消除后续消息的 origin 歧义。凡经 postMessage 交付凭证 / 绑定值,必须先完成 port 转移并经 port 下发(V-13 禁止以 "*" 的裸 postMessage 承载)
    end
```

对 8.1 附加控制菜单的逐项落实:

| 8.1 控制项 | 本协议落点 |
|---|---|
| 一次性不可预测握手值 | `embedSessionId`:CSPRNG ≥ 128 bit,单次嵌入有效,iframe 重载即轮换(§4.5);值经 URL fragment 下发——fragment 不进服务端日志、不受 referer 泄露 |
| 会话绑定 | V-5:每条消息携带 `sessionId`,接收端只接受与本次嵌入一致的值;宿主同时绑定 `event.source` 与其创建的 iframe |
| 消息认证 | 知识证明(对端必须知道 fragment 中的随机值)+ source 绑定;应用层凭证(embed token)的真实性由签名保证,不依赖 postMessage 通道保密性——通道上没有需要保密的值(`esid` 泄露给同页脚本的代价为零:同页脚本本就在选手控制域内,9.2) |
| 序列号防重放 | V-7 高水位:`seq` 严格递增,重放 / 乱序过期消息丢弃 |
| 握手后转移绑定的 MessageChannel | 控制面强化 v1 可选(上图);**凡交付凭证或绑定值则为必需前置**(V-13) |

**明确禁令**:不得把 `event.origin === "null"` 当作信任信号(任何 sandbox 页面的 origin 都是 `"null"`,它不携带任何身份);不得把 `targetOrigin: "*"` 当作唯一信任控制(本协议仅在上图两个方向性不可避免的场景使用 `"*"`,且信任全部建立在附加控制上);**不得经 `"*"` 的裸 postMessage 承载凭证或绑定值**(V-13)。

**残余风险登记(接受)**:opaque 场景下宿主 → 插件的每条消息都携带 `sessionId`(V-5 的绑定字段),故 `esid` 必然经 `"*"` 通道出现;若插件在握手后自行导航,导航后的非预期文档可读到后续消息中的 `esid` 并通过 V-1' / V-5 / V-7 三重绑定——其可注入面仅限控制面消息(`height_changed` 布局扰动,受 `MAX_EMBED_HEIGHT_PX` 与宿主节流约束),不触及任何权威面(动作、投影、判题都在服务端通道)。消除该残余需全量 port 化(T2/T3 选项);v1 以"凭证绝不走该通道"(V-13)+ 控制面影响有界接受之。

### 4.3 版本协商失败路径(宿主不支持协议版本)

- 宿主收到 `hello` 后交集为空(含 `supportedVersions` 不含任何宿主支持版本):**不回 `ready`**,记录事件并按不可用 embed 会话处理;
- 插件在 `T_handshake`(实现期配置)内未收到 `ready` → 进入降级显示(静态提示 + 引导文案,不发起任何会话动作,不向宿主重试风暴——最多按实现期上限重发 `hello`,`seq` 递增);
- 降级显示不是错误注入面:文案为静态资源,不回显任何对端消息内容(避免反射面)。

### 4.4 能力降级路径(13.3:宿主不支持能力)

- `grantedCapabilities` ⊆ `hello.capabilities`(V-8):宿主只授予插件声明过的能力;
- 插件对**未授予**能力必须按禁用实现,逐项降级:

| 未授予能力 | 插件降级行为 | 宿主义务 |
|---|---|---|
| `auto_resize` | 固定高度渲染,不发送 `height_changed` | 忽略一切收到的 `height_changed`(即使收到也调整高度属宿主自由,但不依赖) |
| `theme` | 使用插件内置默认主题 | 不发送 `theme_changed` |
| `language` | 使用插件内置默认语言 | 不发送 `language_changed` |

- `capabilities` 为空数组是合法声明:插件以完全静态形态运行;
- 违反方向的消息(未授予却收到)按 V-8 丢弃 + 计数,不中断会话、不回错误——能力矩阵是发送方的义务清单,不是接收端的状态机输入。

### 4.5 handshake 超时与 iframe 重载(13.3)

- **插件侧超时**:`hello` 发出后 `T_handshake` 未收到 `ready` → 降级显示(§4.3),用户可见的重试入口触发**同会话**重发(`seq` 递增);
- **宿主侧超时**:iframe `load` 后 `T_handshake` 内未收到 `hello` → 标记该 embed 会话不可用,不再投递业务消息(宿主本就不经本通道投递业务数据,此标记仅停止控制面交互);
- **iframe 重载**(8.2 要求支持):宿主生成**新的** `embedSessionId`(如适用同时申请新 embed token),重走 §4.1 完整握手;旧 `sessionId` 立即作废——此后任何携带旧值的消息按 V-5 拒绝;插件侧重载后从空状态重新握手,不继承旧会话的 seq 高水位;
- **重复 / 迟到的握手消息**:握手完成后再收到 `hello`(同会话)→ 状态违规,丢弃 + 计数(V-7 + §三接收端行为要点);`ready` 重发(宿侧重试)→ 插件按 V-7 处理:`seq` 更大则接受并重放幂等的初始化(配置应用是幂等的),`seq` 更小则丢弃。

## 六、embed token 设计(签发与校验流程;实现归阶段五)

### 6.1 参与方与信任锚

- **签发方 = session-api(域 2)**:持有签名密钥(仅域 2 可达)与吊销状态(`token:{jti}`,Redis,带 TTL;WP-1 §二);
- **申请方 = 宿主平台后端**:在接入期于 StackMaster 注册并获得 host 凭证(仅服务端间使用);`tenantId` / `userId` 由宿主后端**从其自身认证上下文派生**后随申请提交——宿主对玩家的认证是宿主的责任,session-api 校验 host 凭证与租户契约,不接触玩家浏览器凭证;
- **持有方 = 浏览器(插件)**:不透明持有,随 create-session 提交。

### 6.2 生命周期(设计)

```text
(接入期)宿主平台注册 → 获得 host 凭证(服务端间)
   ↓
宿主后端 → session-api:签发申请(host 凭证 + tenantId + userId + challengeId + challengeVersion + embedSessionId)
   ↓
session-api:生成 jti → 以域 2 密钥签名 claims(§2.2 七字段)→ 写 Redis token:{jti}(TTL = token TTL ≤ MAX_EMBED_TOKEN_TTL_SECONDS)
   ↓
宿主后端 → 宿主页面 → 插件:token 交付(阶段五决策:服务端模板注入 / 握手后受限下发;禁入 URL query,禁入超会话期存储)
   ↓
插件 → session-api:create-session 携带 token
   ↓
session-api 校验(顺序即设计):
  1. 签名验证(域 2 密钥;失败即拒,不区分原因)
  2. expiresAt 未过、Redis jti 键存在
  3. jti 语义:单用途 → 消费即失效;有限次数 → 原子递减,耗尽即失效
  4. 绑定一致性:create-session 请求中的题目与会话上下文(challengeId / challengeVersion / embedSessionId)
     必须与签名 claims 及签发存储记录(Redis token:{jti} 载荷)三方一致;
     租户 / 用户身份以签发时 host 凭证担保的存储记录为锚(见下方"不采信自报")
   ↓
通过 → 建立 6.2 第 2 条的会话 token 绑定;此后动作走 6.2 统一动作链路(会话凭证由 session-api 另行签发)
```

- **失败响应面**:一切校验失败按 WP-2 语义文档 §七第 8 条产出冻结 `PublicError` 形态,不向浏览器区分"签名错 / 过期 / 已消费"(粗化;细节进域 2 受控日志);
- **吊销**:删除 `token:{jti}` 键即吊销(管理干预路径);TTL 到期自然失效;
- **重载联动**:iframe 重载生成新 `embedSessionId`(§4.5),旧 token 因会话绑定不匹配而自然失效,无需显式吊销(显式删除旧 jti 属可选优化);
- **不采信自报**(WP-1 §1.2 WP-5 红线,锚点冻结):create-session 阶段 session-api 不接触玩家浏览器凭证,插件提交的请求体中**不存在**独立于 token 的身份上下文——租户 / 用户身份的锚点是**签发时 host 凭证担保并持久化的存储记录**(`token:{jti}` 载荷),签名 claims 与该记录一致、请求上下文与两者一致,三方比对通过后 token 在该步骤作为单次 bearer 权威被消费,随即由 session-api 另行签发会话凭证;token 内字段永不接受请求体的未签名复述作为替代。

### 6.3 威胁与缓解对照

| 威胁 | 缓解 |
|---|---|
| token 被同页脚本读取 | 同页脚本本在选手控制域内(9.2);token 是签发记录担保的该玩家自己的短期会话凭证,伪造与窃取不产生越权——服务端校验锚点是签名 + 签发存储记录(`token:{jti}`),而非页面状态;`jti` 单用途消费使窃取窗口以一次为限 |
| 重放旧 token | `jti` 单用途 / 限次 + `expiresAt` + `embedSessionId` 绑定(重载即换) |
| 跨租户 session(13.3) | 签发时 host 凭证与租户契约比对;校验时请求题目上下文与签发记录三方比对,任一不等即拒 |
| 宿主自报身份 / 伪造 token | 签名密钥仅在域 2;无凭证的签发请求拒绝;校验锚点是签发存储记录,不采信请求体身份(6.2 第 1 条) |
| token 进入 URL / 日志 / 长期存储 | 交付纪律(禁 query / 禁超会话存储 / 禁 `"*"` postMessage 承载,V-13);`embedSessionId` 是 fragment 中唯一常驻值且无权限语义 |
| 长期凭证化 | TTL ≤ 7 天外圈护栏(具体值阶段五配置,建议分钟级)+ 单用途 / 限次默认策略 |

## 七、边界声明(8.1 / 9.2,冻结成文)

1. **独立来源 iframe 只隔离宿主页面与插件的 DOM**——CSS、JS 命名空间与脚本错误互不波及;它**不保护插件内的客户端秘密**:iframe 内代码、浏览器 Worker、IndexedDB / localStorage 全部位于选手控制域内,不是服务端安全边界的替代;
2. **真正的秘密保护来自"隐藏状态根本不下发到浏览器"**(9.2):`VmState`、私有题目包、隐藏测试、seed、权威快照、完整 IR 从不离开域 3;本协议通道上因此不存在任何需要保密的值,这是它可以用 `targetOrigin: "*"` + 附加控制完成握手而不引入密码学通道的根本原因;
3. **Shadow DOM 与 Web Component 不是安全边界**:同组织、同源或明确可信平台可用 Web Component 形态嵌入,但隔离承诺为零;题目包或插件代码不可信时,仍应使用独立来源 iframe;
4. **postMessage 的来源校验不能替代 API 认证与授权**(9.2 边界 2):本协议的全部校验只证明"消息来自预期的对端且未经第三方注入",不建立任何服务端权威性;一切权威判定在服务端(6.2 / 9.1);
5. **前端混淆、禁用右键、检测 DevTools 不是反作弊手段**(9.2):有效控制只在服务端串行执行、独立重放、隐藏测试、短期凭证、限流与审计;本协议的 V-1 – V-12 是**完整性与健壮性**规则,不是保密性或权威性规则。
