# StackMaster 项目计划书

## 一、产品定位

### 1.1 核心定位

一个可嵌入、可回放、可解释的 Pwn 概念实验室，而不是浏览器中的完整 Linux 或 x86 模拟器。

由于 AI 的冲击，在 CTF 新生赛中放一些经典的题目的必要性已经丧失，且难以让新生获得学习的正向反馈，所以我们需要一些新的手段去更好的反映、提升新生的水平与兴趣。

因此，该项目将通过一个将内存可视化展现出来的 vm ，让新生通过指定的操作方式直接操作内存来解决 vm 中的谜题来学习 pwn 的基础知识。同时为了方便各靶场引入该项目，项目将以 Web 插件的形式去实现。

同时为了具备更好的可拓展性，项目将允许出题人更加方便地去修改虚拟指令集、方法、寄存器和内存布局，这意味着项目将具备一定程度的框架属性。

### 1.2 安全定位

本项目采用“**后端权威 VM、浏览器公开投影**”的安全模型：

- 完整 VM Core、完整 VM 状态、私有题目包、隐藏测试、权威目标条件、随机种子、完整快照和内部事件日志只允许存在于后端；
- 浏览器是不可信任的可视化客户端，只负责题面展示、Payload 构造、用户交互和公开状态渲染；
- 学习者操作的是远程 VM 会话，而不是浏览器内的完整 VM；
- 即使选手读取或篡改浏览器内存、脚本、本地存储和网络消息，也无法获得隐藏关键信息，也不能影响正式成绩。

之所以不把 VM Core 放在浏览器 Web Worker 中运行，是因为 Worker、iframe、代码混淆和浏览器本地存储都不构成选手侧的安全边界：选手对自己浏览器内的代码和内存拥有完全控制权。唯一可靠的做法是让隐藏状态根本不进入浏览器。

## 二、目标用户

### 2.1 Pwn 初学者

主要需求：

- 通过内存可视化去直观地分析谜题；
- 通过服务端会话中指定的操作实时调试谜题；

次要需求：

- 认识地址、字节、十六进制、端序和基本寄存器；
- 学习基础的汇编指令和机器码；
- 观察内存区域划分、寄存器与指令的相互作用等核心现象；
- 认识 elf 结构，如 .plt、.got、.bss、.text等；
- 掌握 gadget 的运用；
- 熟悉栈的操作、栈迁移、栈风水；
- 获取分级提示；

### 2.2 出题人

主要需求：

- 通过公开描述包和私有判题包分别配置题面信息与完整初始状态；
- 向选手指定 syscall 接口、可用操作；
- 声明成功条件和资源限制；

次要需求：

- 编写分级提示，控制提示信息逐步增加；
- 通过题目包和版本机制维护多道渐进式题目；

### 2.3 CTF 平台维护者

主要需求：

- 在静态 HTML、CTFd、Vue、Angular、Django 模板或自建平台中接入；
- 不强制宿主安装特定前端框架；
- 允许插件独立发布、升级、回滚和故障恢复；
- 通过服务端接口完成正式提交和成绩裁决；

次要需求：

- 允许较为方便地对项目进行扩展开发以满足复杂需求；

## 三、产品范围、边界与非目标

### 3.1 产品范围

本项目建设的是一个 **基于可视化内存 VM 的 pwn 教学和题目框架** ，包括：

- 受限的 VM 状态和操作模型，完整实现在后端隔离环境中；
- 后端权威 VM 会话：单步、运行、暂停、回退、checkpoint、时间线和回放均由服务端执行；
- 内存、寄存器、栈帧和控制流的可视化，数据来自服务端脱敏公开投影；
- ASLR、PIE、Canary、NX 等保护的支持；
- Payload 构造、回放和错误解释；
- 声明式题目格式（公开描述包 + 私有判题包）与出题人扩展机制；
- 可嵌入不同 CTF 平台的 Web 插件；
- 服务端权威会话执行、独立裁决与审计接口。

### 3.2 明确的非目标

MVP 阶段不追求把项目做成完整 CPU 或操作系统模拟器，因此暂不包括：

- 完整 x86-64 指令集；
- ELF 加载器和任意 ELF 上传；
- 完整 Linux、真实 shellcode 或任意 C/Python/JavaScript 执行；
- 完整 glibc、真实容器或任意系统调用；
- 复杂堆分配器、多架构兼容；
- 在线题目编辑器；
- AI 自动生成 exploit；
- 多人实时协作、排行榜和其他未服务于首个教学闭环的功能。

同时，基于安全模型的边界，本项目**不**包括：

- 浏览器端完整 VM Core 或任何形式的本地权威执行；
- 无后端环境下继续执行权威 VM 或完成判题；
- 将完整 VM Core、私有题目包或隐藏状态下载到浏览器后，以代码混淆、Web Worker、iframe 或 WASM 方式保护；
- 浏览器本地判题作为服务端判题的替代方案。

## 四、核心功能

### 4.1 学习者使用流程

```text
加载公开题目描述
→ 创建服务端 VM 会话
→ 观察内存布局（公开投影）
→ 通过受限动作构造 Payload 并发送给服务端
→ 接收脱敏投影并查看内存、寄存器和控制流变化
→ 获得错误解释或分级提示
→ 请求服务端回退到检查点
→ 调整 Payload
→ 重放并提交
```

系统应允许学习者在理解过程中保留试错记录，而不是只保留最后一次提交。

同时 payload 将采用积木式的操作来搭建，且允许学习者在 payload 中设置断点。

断线时浏览器只展示最近一次收到的公开投影，不在本地继续执行 VM。

### 4.2 内存和执行状态可视化

至少提供以下面板：

- 题目目标、当前概念、执行步数和提示等级；
- 结构化内存视图，展示代码区、全局区、栈区和关键对象等；
- 字节视图，展示地址、十六进制字节、ASCII 和语义归属；
- 寄存器面板，重点展示 `RSP`、`RBP`、`RIP` 以及题目使用的通用寄存器；
- 调用栈和控制流变化；
- Payload 构造器和最终字节偏移。

额外可以考虑实现的部分：
- 当前状态与上一次状态的 diff；

以上所有数据均来自服务端生成的公开状态投影，浏览器不做本地推导或重建。

结构视图和字节视图必须联动：点击 `return address` 时高亮对应字节，点击 payload 字节时显示其覆盖的对象；颜色和文本应区分用户输入、程序写入和初始数据。

### 4.3 Payload 构造器

Payload 不应只通过一个黑色终端输入框输入。可提供以下字节块进行积木拼接：

- 填充，例如 `A × 40`；
- 原始字符串；
- 整数值；
- 地址；
- 空字节；
- 已编码字节。

每个字节块应显示逻辑值、实际字节、长度、端序和在最终 payload 中的偏移。系统可以提供辅助解释，但不应默认替学习者计算所有关键偏移或自动修正端序。

同时允许用户自定义封装特定 payload 进行复用等复杂操作。Payload 草稿可以本地编辑，但实际执行动作必须发送到服务端验证。

### 4.4 执行、回退和反馈

支持以下执行粒度（均由服务端会话执行）：

| 模式 | 用途 |
|---|---|
| 运行到结果 | 快速验证题目是否完成 |
| 执行到关键事件 | 在 `call`、`ret`、`syscall` 或异常处暂停 |
| 单条机器动作 | 理解寄存器和控制流变化 |
| 单字节 diff | 排查 payload 覆盖范围 |

必须支持运行、暂停、单步、上一步、重置、创建 checkpoint、时间线拖动和回放。这些能力全部以服务端动作形式提供：浏览器发送 `step`、`undo`、`checkout-checkpoint`、`reset` 等会话命令，服务端执行后返回新的公开投影；浏览器时间线只保存 revision 和 checkpoint 引用，不保存也不重建完整状态。

错误反馈不应只显示：

```text
Segmentation fault
```

而应解释：读取或写入发生在哪个地址、该值被如何解释、为什么不在可执行或可写区域，并提示学习者检查 padding、little-endian 和 `RSP` 位置。错误类型至少覆盖输入格式错误、payload 长度错误、偏移不足或过长、端序错误、权限错误、非法 `RIP`、Canary 破坏、参数寄存器错误以及目标条件未满足。错误解释由服务端按 ProjectionPolicy 生成脱敏版本后下发，不得泄露隐藏区域或私有目标条件的细节。

提示采用逐级增加信息的方式，例如：

```text
Hint 1：观察 RBP 和 RSP。
Hint 2：找出 buffer 与 return address 的距离。
Hint 3：计算需要填充的字节数。
Hint 4：检查目标地址的 little-endian 表示。
```

## 五、技术路线与总体技术架构

### 5.1 技术路线总览

技术路线遵循一条主线：

```text
TypeScript 服务层 + Rust VM Engine 做出"正确、可解释、可回放"的后端权威最小闭环（T0）
→ 安全评审驱动的隔离强化（T1）
→ benchmark 与教学数据驱动的性能与能力扩展（T2 / T3）
```

每个阶段有明确的进入与退出条件，触发条件满足前不引入更复杂的技术：

| 阶段 | 对应开发阶段 | 技术主题 | 进入条件 | 退出条件 |
|---|---|---|---|---|
| T0 最小闭环 | 阶段一～五 | TypeScript 服务层 + Rust VM Engine、单实例编排器、每会话独立 Rust Worker 进程、Docker Compose | 项目启动 | MVP 验收（第十一章、13.6）通过 |
| T1 隔离强化 | 阶段六 | 容器级 Worker 隔离、verifier 独立部署、租户预算与审计完善 | MVP 上线试用 | 9.2 威胁模型测试与 13.5 秘密零驻留测试通过，裁决可复现 |
| T2 规模与性能 | 后续演进 | 多实例编排器 + Redis Streams、WSS 网关分离、投影二进制编码 | 10.3 工程目标或并发容量出现真实瓶颈（benchmark 证据） | 工程目标达成，容量满足第十五章运营观察 |
| T3 能力扩展 | 后续演进 | 堆、ROP、更多防护机制、真实 ELF 实验模式 | T0/T1 指标稳定且教学数据支持（第十五章） | 以实际教学效果评估决定 |

**路线纪律**：K8s、Kafka/NATS 等消息中间件、微服务拆分、二进制投影编码、VM Core 的 WASM 化均属于 T2/T3 选项，触发条件满足前不得引入；未触发前的工程精力优先投入正确性、可解释性和测试覆盖。这与第十四章"过早引入低层优化"的风险应对一致。

### 5.2 总体框架：四个信任域

总体框架落实 9.2 的四边界安全模型，并将基础设施落到具体层：

```text
═════ 信任域 1：浏览器展示域（完全不可信）═════
  宿主 CTF 平台（静态 HTML / CTFd / Vue / Angular / Django）
     │ iframe（独立来源）+ postMessage 嵌入协议（仅加载、主题、生命周期）
     ▼
  插件 Shell（Lit Web Components，运行于插件独立来源 iframe）
     ├── 题目描述加载器：仅加载公开描述包（CDN，带哈希/签名）
     ├── Payload 构造器与可视化 UI：只渲染公开投影
     ├── 本地状态（IndexedDB）：UI 偏好、Payload 草稿、脱敏投影缓存
     └── 会话协议客户端：HTTPS REST + 认证 WSS
          │
═════ 信任域 2：接入编排域（无秘密，可水平扩展）═════
          ▼
  会话编排器（Fastify，无状态）
     ├── 认证 / 授权 / 限流 / 租户隔离（embed token 绑定校验）
     ├── 会话生命周期、revision 预检与幂等键管理
     ├── 单会话动作串行化与会话路由
     └── Redis：限流计数、幂等键（TTL）、路由表、token 缓存
          │
═════ 信任域 3：权威执行域（秘密驻留区，无网络出口）═════
          ▼
  VM Worker（Rust vm-worker 可执行文件，每会话独立进程；T1 起容器化）
     ├── vm-core：VmState、受限 IR 解释、教学伪 syscall
     ├── 私有题目包、隐藏测试、seed 与权威目标条件
     ├── vm-runtime：COW 快照、规范化动作日志、回放
     ├── projection：ProjectionPolicy 白名单与脱敏
     └── 持久化：PostgreSQL（会话、动作日志、快照、提交、裁决、审计）
                对象存储（私有判题包、诊断 trace）
          │
═════ 信任域 4：裁决审计域（独立部署）═════
          ▼
  独立 verifier：重放规范化动作日志、隐藏测试裁决、审计
  管理后台：独立凭证与网络域，不出现在插件链路中
```

投影在信任域 3 内部生成完毕后才离开执行域，因此信任域 2 与网络通道上只有公开投影。三条由结构保证（而非流程约定）的规则：

1. **秘密不出执行域**：`VmState`、私有题目包、隐藏测试和 seed 只存在于 VM Worker 进程内（ADR-7）；
2. **跨域只传投影**：编排器、通道与浏览器任何位置都不持有完整 VM 状态；浏览器、TypeScript 服务与 Rust 引擎只共享 `protocol` 包导出的 JSON Schema 契约（协议类型、公开数据类型和错误类型），不共享权威 VM 实现代码；
3. **构建期隔离可机器验证**：Rust 引擎 workspace（`vm-core`、`vm-runtime`、`projection`）与 `challenge-compiler` 只存在于后端构建产物，CI 对浏览器产物做导入图与产物扫描（5.8），使隔离成为可验证的性质。

### 5.3 运行时拓扑与动作数据流

T0 拓扑（标注 T1/T2 演进）：

```text
CDN / 静态托管：插件静态资源、公开描述包（带哈希/签名）
宿主 CTF 平台 ──iframe──▶ 插件 Shell（浏览器）
                             │ HTTPS：会话生命周期、提交、embed token 签发
                             │ WSS：动作、ProjectionDelta
                             ▼
会话编排器（Fastify，无状态，T2 起多实例）
   ├── Redis：限流、幂等键（TTL）、会话路由、token 缓存
   ├── 会话队列：进程内队列（T0）→ Redis Streams（T2 多实例时）
   └── VM Worker 池：Rust vm-worker 进程（stdio / 本地 socket JSON 协议；T1 起容器化），无网络出口
          ├── PostgreSQL：会话、规范化动作日志、快照、提交、裁决、审计
          ├── 对象存储（MinIO / S3 兼容）：私有判题包、诊断 trace
          └── 投影由 Worker 生成后原路返回编排器
提交时：独立 verifier 读取规范化动作日志，重放并裁决（独立部署）
```

一次动作的端到端数据流：

```text
1. 浏览器发出 ActionRequest（携带 baseRevision 与 idempotencyKey）
2. 编排器校验 token 绑定、租户配额、限流、幂等，并预检 revision，入队
3. 会话绑定的 Worker 以私有题目包 + 当前 VmState 执行动作，
   追加私有事件与规范化动作日志
4. Worker 检查权威目标条件与资源预算
5. Worker 按 ProjectionPolicy 生成 PublicStateProjection / ProjectionDelta
   （白名单 + 脱敏在离开执行域之前完成）
6. 编排器更新会话 revision 并经 WSS 下发浏览器
7. 提交时，独立 verifier 重放规范化动作日志并做最终裁决
```

会话粘性与恢复：活跃会话绑定到一个 Worker 进程；进程崩溃或被强制终止时，编排器从最近服务端快照替换恢复（9.1），浏览器只通过 `sync-projection` 重新同步，不参与恢复。编排器自身无状态：路由在 Redis，权威状态与快照在 PostgreSQL，编排器重启不破坏会话一致性。

### 5.4 技术选型与关键决策

| 层 | 领域 | 选型 | 作用 |
|---|---|---|---|
| 浏览器 | UI 组件 | Lit 3 + TypeScript | 框架无关的 `<pwn-memory-vm>` 与教学 UI |
|  | 构建 | Vite（library mode 多入口） | iframe 应用、Web Component、包装器分别打包 |
|  | 渲染 | 语义化 DOM + lit-virtualizer + SVG | 字节视图、大规模列表、控制流关系 |
|  | 本地状态 | IndexedDB（idb-keyval） | UI 偏好、Payload 草稿、脱敏投影缓存 |
|  | 辅助线程 | Web Worker（可选） | 仅公开投影合并与渲染辅助，不运行 VM |
| 协议 | 契约 | `@stackmaster/protocol`（Zod → JSON Schema） | `ActionRequest`、投影与错误类型；JSON Schema 为跨语言契约唯一来源 |
|  | 题目包校验 | JSON Schema 2020-12 + Ajv | 公开/私有题目包校验，跨语言可实现 |
| 传输 | REST | HTTPS + Fastify | 会话生命周期、提交、embed token 签发 |
|  | 流式 | 认证 WSS（@fastify/websocket）+ JSON 消息 | 动作与 ProjectionDelta；二进制帧仅在 benchmark 证明必要时评估 |
| 服务 | 运行时 | Node.js LTS（≥22） | 编排器与 verifier 服务运行时 |
| 执行 | VM 引擎 | Rust（safe Rust，`#![forbid(unsafe_code)]`） | u64 地址与端序一等公民；无 IO、无时钟依赖、随机源注入（6.3 确定性） |
|  | 跨语言边界 | 进程边界（stdio / 本地 socket + JSON 协议） | 编排器按会话 spawn `vm-worker`；禁止 FFI / N-API 内嵌 |
|  | 隔离单元 | 每会话独立 Rust Worker 进程 → 容器（T1） | 权威执行、资源限制、强制终止、崩溃恢复 |
| 数据 | 主存储 | PostgreSQL 16+ | 会话、动作日志、快照、提交、裁决、审计 |
|  | 辅助存储 | Redis 7+ | 限流、幂等键（TTL）、会话路由、token 缓存 |
|  | 对象存储 | MinIO（dev）/ S3 兼容（prod） | 私有判题包、trace、公开包发布产物 |
| 工程 | 仓库 | pnpm workspaces + Turborepo + Cargo workspace | 双 workspace 单仓、任务编排与构建缓存 |
|  | 测试 | Vitest + fast-check、cargo test + proptest、Playwright、axe-core、k6 | 单元/属性测试、E2E 与嵌入、无障碍、负载 benchmark |
|  | 边界强制 | dependency-cruiser + ESLint + cargo clippy | 依赖方向约束、引擎确定性约束 |
|  | 可观测 | Pino / tracing + OpenTelemetry + Prometheus | 日志、链路追踪、指标（对接第十五章） |
|  | CI/CD | GitHub Actions + Changesets | 质量门禁、隔离扫描、npm 发布 |

关键技术决策（ADR 摘要）：

- **ADR-1（语言分层）服务层与前端 TypeScript，执行域 Rust VM Engine（修订原"全栈单一语言"决策）。** 单一语言的价值（类型共享）改由跨语言契约机制承担（ADR-5、ADR-8）。修订动因：pwn 教学语义即内存破坏，所有权系统在实现层直接排除别名类缺陷；u64 地址与 little-endian 是教学核心且为 Rust 一等公民；确定性由语言与工具链（overflow-checks、miri、fuzz）保证而非 lint 纪律；无 GC 进程使每会话内存从几十 MB 降至个位数 MB，提升并发密度与资源韧性。注意 Rust 收益来自安全与语义保真，而非速度——动作粒度为教学动作级，Node.js 性能本就足够。否决 Python/FastAPI 混合栈不变（类型共享断裂，双生态成本，再叠加 Rust 边界只会更糟）。
- **ADR-2（服务框架）Fastify。** 内置 JSON Schema 校验（Ajv）、`@fastify/websocket`、限流与精确来源 CORS 插件齐全。否决 Express（schema 与类型能力弱）与 NestJS（抽象层对 MVP 无收益）。
- **ADR-3（隔离单元）每会话独立进程（T0），T1 起容器化。** 教学规模内存使进程级隔离的复制与恢复成本可接受，满足强制终止与崩溃后快照替换恢复（9.1）；容器每会话成本与冷启动在 MVP 不划算。进程体为 Rust `vm-worker` 可执行文件，经 stdio / 本地 socket 以 JSON 协议与编排器通信；禁止以 FFI / N-API 形式嵌入 Node 进程，以保留崩溃隔离与信任域完整。T1 起按赛事弹性与租户预算切换容器池：cgroup CPU/内存上限、只读文件系统、禁网络出口。
- **ADR-4（数据基础设施）PostgreSQL 为唯一权威存储，Redis 只存可重建状态，对象存储放大对象。** 动作日志（append-only）、提交、裁决与审计需要事务与强一致语义；Redis 中的限流计数、幂等键、路由表均带 TTL、可重建，不作为权威；快照为小 blob 存 PostgreSQL，私有判题包与诊断 trace 存对象存储（服务端专用桶、静态加密、最小权限）。
- **ADR-5（契约）`protocol` 包单一来源，JSON Schema 为跨语言权威。** Zod schema 同时产出静态 TS 类型与 JSON Schema；JSON Schema 是 TypeScript 与 Rust 的共同契约，Rust 侧以 serde + schemars 消费（ADR-8）；题目包面向跨语言工具链，以 JSON Schema + Ajv 校验；服务端对一切入站数据（HTTP、WSS、postMessage 转发的动作）按同一契约重新校验，不信任客户端类型标注。否决 tRPC（核心是受限动作协议而非 RPC 面，公开描述包走静态分发）与 gRPC（浏览器侧需代理层，MVP 复杂度不划算）。
- **ADR-6（工程结构）pnpm workspaces + Turborepo。** 单仓多包保证协议类型即时同步；对外发布的包（`web-component`、`react-wrapper`、`embed-runtime`）用 Changesets 走 npm。否决多仓（协议同步成本高）与 Nx（能力重叠且更重）。
- **ADR-7（投影生成位置）在 Worker 域内生成投影。** 白名单与脱敏发生在数据离开执行域之前，编排器与网络通道只见公开投影；这使"编排器被攻破也不泄露秘密"成为结构性质，而非运维约定。
- **ADR-8（执行域）Rust VM Engine，以进程边界交付。** Rust 范围锁定为纯同步状态机 crate：`vm-core`（VM 语义）、`vm-runtime`（COW 快照、规范化动作日志、回放、私有题目包加载）、`projection`（ProjectionPolicy 评估，保证 ADR-7 在执行域内完成）；全部 crate 级 `#![forbid(unsafe_code)]`，release 构建 `overflow-checks = true`，时钟与随机源由 trait 注入（6.3），无 async、无直接 IO。交付形态为 `vm-worker` 可执行文件，由编排器按会话 spawn（ADR-3）。verifier 复用同一 Rust 回放实现做最终重放——"交互执行与裁决重放是同一份引擎代码"，消除双实现分歧；verifier 的独立部署与流程独立（9.1）不变。**回退预案**：若阶段一结束时无 Rust 产能，回退为 TypeScript vm-core；由于协议已 JSON Schema 化并保持 golden fixture 纪律，回退与后续替换成本均有界。

React 和 Vue 可以提供薄包装器，但不作为主插件接口。项目的主要跨平台接口优先选择原生 Web Component；默认的跨域分发形态优先选择独立来源 iframe。

```text

vm-core             ← vm-runtime、projection、vm-worker
vm-runtime          ← vm-worker
projection          ← vm-worker

跨语言规则：TS 构建图不得引用 vm-engine 任何产物；vm-engine 只以进程边界
（spawn + JSON 协议）被 session-api 与 verifier 使用；IR 与题目包是版本化
```

**VM Core 不应该知道自己运行在 Lit、React、iframe、Node.js 还是哪个操作系统中；同时它只运行在后端。** 浏览器不得加载、执行或缓存完整 VM Core、可执行 IR、私有题目包、权威快照、隐藏测试或服务端 seed。vm-core 与 vm-runtime 全部使用 safe Rust（crate 级 `#![forbid(unsafe_code)]`），禁止使用 `std::time`、`rand`、`std::io`、`std::net` 与文件系统，时钟与随机源由 trait 注入；release 构建 `overflow-checks = true`，以满足 6.3 的确定性要求（clippy lint 与 CI 构建脚本强制）。

### 5.6 接口契约与版本化

项目共有三类契约，全部以 `protocol` 与 `challenge-schema` 包为单一来源：

1. **嵌入协议**：宿主平台 ↔ iframe 插件 Shell 的 postMessage 消息（8.2），版本化消息信封；
2. **会话动作协议**：浏览器 ↔ 编排器的 `ActionRequest` / `ActionResponse`（6.2），Zod 契约即校验；
3. **题目包 Schema**：作者工具链 ↔ 平台的公开/私有题目包 JSON Schema（第七章），跨语言可实现；
4. **引擎进程协议**：编排器 / verifier ↔ Rust vm-worker 的 JSON 协议，复用同一份 `ActionRequest`、投影与错误 Schema，不另造私有格式。

版本化策略：每类契约携带独立 `protocolVersion` / `schemaVersion`；破坏性变更递增版本号并保留 N-1 兼容窗口（过渡期同时接受两个版本，窗口期结束下线旧版）；错误类型同样是契约，`PublicError` 枚举与 9.1 的结果类型保持稳定，前端不得解析非契约字段。Rust 侧以 serde + schemars 消费同一 JSON Schema；CI 维护一组 golden fixture（典型动作、非法动作、投影样例），同一组样例必须被 TS 与 Rust 校验器同时接受或拒绝，且规范化 JSON 序列化一致，防止双语言实现漂移。

## 六、VM 语义与状态模型

### 6.1 MVP 的虚拟硬件

VM 架构位宽（`archBits`）由出题人在 VM Profile 中声明，取值域为 `{32, 64}`（v1 冻结二元；扩展走 VM Profile Version）。架构值按位宽定义，内部以 64 位容器承载、高位按位宽掩蔽（见 6.2）。

MVP 的虚拟内存以 VMA 为基本单元（全部由后端 VM Core 实现），每个 VMA 的权限（`r`/`w`/`x`）、类型与大小均由出题人设定：

- 类型为封闭枚举：代码区、全局区、堆区、栈区、关键区，以及出题人自定义命名的 `custom` 类型；
- 大小必须为 4KB 的倍数（页大小同为 4KB 倍数区间）；区域内部的缓冲区、canary 等教学对象不受对齐约束。

寄存器的名称、数量由出题人在 VM Profile 中声明（v1 覆盖通用寄存器类；浮点、向量等非通用寄存器类走 VM Profile Version 演进），但受以下边界约束：

- 必选核心寄存器 `RSP`、`RBP`、`RIP` 必须存在——会话动作（`push`/`pop`/`call`/`ret`）、栈语义指令（含 `leave`）与 MVP 教学闭环（栈帧/缓冲区/返回地址）均建立在其上；
- 一般寄存器命名不得落入 `FLAG` 前缀保留区；FLAG 寄存器承载题目秘密，值永不进入公开面；
- 名称与数量上限是资源护栏（内存布局与投影体积约束），不是自由度限制。

MVP 基线指令集为封闭 opcode 集：`mov`、`push`、`pop`、`leave`、基本算术与位运算（`add`、`sub`、`cmp`、`and`、`or`、`xor`、`shl`、`shr`）、有限跳转、`call`、`ret`、`syscall`。MVP 的操作不要求等同于完整机器指令，应优先服务于概念解释。在此基础上，出题人可以在私有题目包中以声明式映射表定义"指令作用 ↔ 机器码表现"的映射（自定义指令与 `syscall`/`call` 可调用的作者接口，见 7.2）。这里的 `syscall` 只是固定、有限、无宿主副作用的教学伪操作，不提供真实操作系统调用语义；派发到作者接口的调用同样不产生宿主副作用。

### 6.2 状态模型与统一动作链路

核心状态分为三层：

```ts
// 仅存在于后端隔离环境
interface VmState {
  registers: Registers;
  memory: VirtualMemory;
  callFrames: CallFrame[];
  instructionPointer: InstructionPointer;
  privateEventLog: VmEvent[];
  constraints: RuntimeConstraints;
  seedState: SeedState;
  status: "running" | "paused" | "won" | "failed";
}

// 允许发送到浏览器
interface PublicStateProjection {
  revision: number;
  visibleRegions: VisibleMemoryRegion[];
  visibleRegisters: PublicRegister[];
  callStackSummary: PublicCallFrame[];
  controlFlow: PublicControlFlow;
  semanticHighlights: SemanticHighlight[];
  status: PublicStatus;
}

// 投影策略：决定公开投影的内容边界
interface ProjectionPolicy {
  visibleRegions: string[];
  visibleObjects: string[];
  visibleRegisters: string[];
  maxBytesPerRange: number;
  errorDetailLevel: "coarse" | "educational";
}
```

`VmState` 是服务端私有类型，不得通过 API、WebSocket、postMessage、浏览器 Worker、IndexedDB 或回放下载接口返回给浏览器。浏览器只接收根据 ProjectionPolicy 生成的公开投影和增量。

所有状态变化必须经过统一入口：

```text
ActionRequest
→ 认证、授权、会话与 revision / 幂等校验
→ 服务端 VM 状态转换
→ 私有事件与私有状态更新
→ 私有目标条件检查
→ ProjectionPolicy 白名单与脱敏
→ ActionResponse / ProjectionDelta
```

动作请求和响应的协议基线：

```ts
interface ActionRequest {
  protocolVersion: number;
  sessionId: string;
  clientSeq: number;
  baseRevision: number;
  idempotencyKey: string;
  action: {
    type:
      | "write_bytes" | "push" | "pop" | "call" | "ret"
      | "step" | "run_to_event" | "pause"
      | "undo" | "checkout_checkpoint" | "reset"
      | "create_checkpoint";
    args: unknown;
  };
}

interface ActionResponse {
  requestId: string;
  revision: number;
  status: "running" | "paused" | "won" | "failed" | "rejected";
  projectionDelta: ProjectionDelta;
  publicEvents: PublicEvent[];
  userVisibleError?: PublicError;
}
```

服务端必须：

1. 从认证上下文派生用户、租户、题目和题目版本，不接受请求体自报身份；
2. 校验会话 token 绑定（租户、用户、题目版本、iframe 会话、过期时间）；
3. 校验 `baseRevision` 与当前状态一致，拒绝过期 revision；
4. 以 `idempotencyKey` 防止重复执行；
5. 在单会话内串行处理动作；
6. 对动作参数、地址、区域权限、操作数和资源预算重新校验；
7. 只从服务端题目包和服务端 VM 状态执行。

禁止返回：`VmState`、完整内存或寄存器、原始私有事件、完整状态哈希、私有 IR、隐藏目标条件的判断细节，以及可用于推断隐藏字节的长度、时序或差异信息。

浏览器不得提交自制快照、最终状态、状态哈希或成功标志来覆盖服务端状态；一切状态变化只能通过服务端动作发生。

地址在 VM Core 中优先使用 `bigint`。架构值的宽度由题目 `vmProfile.archBits` 声明（32 或 64）：架构值是 archBits 宽的值，以 64 位容器承载，高位按位宽掩蔽，全部算术、移位与比较在掩蔽域内进行；出界与进位/借位行为在指令规约中按位宽定义。题目 DSL 和公开 API 使用明确的十六进制字符串。这是后端实现细节；浏览器只处理公开投影中的地址字符串和范围。

### 6.3 确定性与可回放

回放和撤销全部由服务端托管：

- 服务端保存完整动作日志和周期性 Copy-on-Write 快照；
- 客户端时间线只保存 revision 和 checkpoint 引用，不保存完整状态；
- `undo` 和 `checkout` 请求由服务端验证归属后恢复权威状态，并重新生成公开投影；
- 浏览器不得根据本地缓存重建私有状态。

每次操作至少记录操作类型和参数、前后状态哈希、内存与寄存器变化、事件序号、题目版本、VM Profile 和引擎版本。

回放不得依赖当前时间、浏览器随机数、网络响应顺序、宿主线程调度或浏览器未定义行为。题目需要随机化时，应使用可复现的服务端 seed，并将 seed 策略和运行环境版本写入回放信息。

内存按固定大小分页，并在服务端采用 Copy-on-Write 快照，避免每一步复制完整 VM 状态。

## 七、题目 DSL 与出题人扩展机制

### 7.1 题目双包模型与发布流程

出题人扩展能力必须是受控的框架能力，而不是任意代码执行能力。题目包分为两个物理和逻辑上分离的部分：

**公开描述包（Public Challenge Descriptor）**，可被浏览器读取，只包含：

- 题面、学习目标和教学文案；
- VM Profile 的公开元数据；
- 可见区域布局和公开对象标签；
- 允许动作及参数 Schema；
- 资源限制的公开部分；
- 提示阶梯和公开错误映射；
- UI 所需的非秘密初始投影。

**私有判题包（Private Challenge Bundle）**，只存在服务端，包含：

- 完整初始内存和寄存器；
- 隐藏 flag、隐藏字节和虚拟文件内容；
- 私有对象和隐藏区域；
- 权威成功/失败谓词和隐藏测试；
- seed 策略和服务端随机状态；
- 编译后的 IR 和题目专用判题配置。

发布流程为：

```text
作者 DSL
  → JSON Schema 校验
  → 静态检查
  → 字段分类检查（public / private 严格分离，禁止混装）
  → 编译为受限 IR（只进入私有判题包）
  → 生成公开描述包与私有判题包
  → 签名、哈希和发布
```

公开描述包不包含可在浏览器中独立执行 VM 所需的完整初始状态、Runtime、IR、目标评估器或随机化材料；浏览器必须通过后端 VM 会话请求执行动作。

### 7.2 可扩展内容

在版本和安全约束下，出题人可以配置或组合：

- 虚拟指令集或允许的操作；
- 指令作用与机器码表现的映射（自定义指令与作者接口的声明式定义）；
- 方法、调用机制和操作注册表（`syscall`/`call` 派发的作者接口面）；
- 寄存器集合及其展示语义（名称与数量可声明，边界见 6.1）；
- 代码、全局、堆、栈、关键区域及自定义命名类型的内存布局（VMA 权限、类型与 4KB 倍数大小）；
- 教学对象、引用关系和可视化标签；
- 成功、失败和资源限制条件；
- 多阶段题目的有限状态机。

这里的“扩展”分两层。**基线层**：选择固定 Runtime 中经过审计的内置 opcode、predicate 和操作 ID，并配置其受 Schema 约束的参数。**声明层**：在私有题目包内以声明式映射表（数据）定义“指令作用 ↔ 机器码表现”的映射——自定义指令是封闭微算子原语的有序组合（v1 仅直线语义、恒定步数），作者接口是封闭效果原语的有序列表（如 `exit`、`grant_virtual_file`、`virtual_file_read`、`set_flag`、`noop`），供 `syscall`/`call` 派发。映射表由引擎按封闭原语集解释执行；题目包不得动态注册处理函数、加载模块或注入新的执行代码。若未来新增基线指令语义，应作为经过审核、测试和版本化的 Runtime 发布，而不是随题目包运行时加载。

多阶段题目中的每个状态应包含允许操作、前置条件、迁移条件、有限副作用、失败条件和资源预算。循环必须有静态上限或动态指令预算。

### 7.3 DSL 的安全边界

客户端题目包只能包含教学所需的公开状态；隐藏 flag、隐藏测试、私有目标条件和服务端判题秘密只能存在服务端。`virtual_file:flag` 一类 capability 为服务端专用，不得出现在客户端题目包、公开事件、公开回放或公开投影中。

编译后的完整 IR 只部署到后端。浏览器如果需要展示伪指令，只接收服务端从展示数据单独生成的文本，不接收可执行 IR。

题目 DSL 不设计成脚本语言，不允许：

- JavaScript、Python、Lua 等任意回调；
- `eval`、`Function` 或动态导入；
- 用户自定义函数和任意 WebAssembly；
- 文件系统、网络、进程和宿主对象访问；
- 无限循环、无限递归和动态拼接 capability 名称。

出题人声明的自定义指令与作者接口不改变上述边界：它们是封闭原语（微算子/效果原语）的有序组合，属于受 Schema 约束的声明式数据，由服务端引擎解释执行，不构成脚本语言或任意回调。自定义指令 v1 仅直线语义（不含控制转移，CFG 静态分析保持），每条自定义指令与接口效果的求值步数恒定、与操作数值无关；其内存访问走统一权限检查与统一拒绝路径，效果可见性遵守投影白名单。

表达式只支持常量、只读寄存器引用、命名内存区域查询、有界整数和位运算、比较、布尔组合、固定长度切片、有界字节匹配及枚举值比较。复杂逻辑优先沉淀为经过审计的内置谓词。

### 7.4 版本管理

至少区分以下版本：

1. DSL Schema Version；
2. VM Engine Version；
3. VM Profile Version；
4. Challenge Content Version。

正式判题和回放还应记录题目包哈希、VM Profile 哈希、引擎构建 ID、判题规则版本、随机种子策略和规范化提交内容哈希。生产环境不得自动使用“最新引擎”，正式题目应锁定执行环境。

## 八、插件嵌入、协议与部署

### 8.1 默认嵌入形态

默认采用跨域、独立来源的 iframe：

- 宿主平台不需要安装前端依赖；
- 避免宿主 CSS 污染插件；
- 插件可以独立发布、升级和回滚；
- 兼容不同语言和前端框架；
- 插件异常时较少影响宿主页面。

iframe 应使用最小化的 `sandbox` 权限，并谨慎处理 `allow-same-origin`；不应把长期凭证放入 iframe URL。推荐的独立来源方案应保持插件来源与宿主不同，并由稳定的插件来源配合严格的 `event.origin`、`event.source` 和 `targetOrigin` 校验；不要在与宿主同源的 iframe 中同时使用 `allow-scripts allow-same-origin`。如果采用不带 `allow-same-origin` 的 opaque origin sandbox，则不能仅凭 `event.origin` 为 `"null"` 信任消息；向 opaque origin 发送消息时可能必须使用 `targetOrigin: "*"`，但必须同时依赖预期的 `event.source`、一次性不可预测的握手值、会话绑定、消息认证、序列号和重放校验，或在握手后转移到经过绑定的 `MessageChannel`，不能把 `"*"` 作为唯一信任控制。

必须明确：独立来源 iframe 只隔离宿主页面与插件 DOM，**不保护插件内的客户端秘密**。真正的秘密保护来自“隐藏状态根本不下发到浏览器”。iframe 内代码、浏览器 Worker 和本地存储都在选手控制域内，不能作为服务端安全边界的替代。

同组织、同源或明确可信的平台可以使用 Web Component，但必须明确：**Shadow DOM 和 Web Component 不是安全边界。** 题目包或插件代码不可信时，仍应使用独立来源 iframe。

### 8.2 嵌入协议与会话动作协议

项目涉及两层协议：

**postMessage 嵌入协议**：仅承担宿主平台与 iframe 插件 Shell 之间的加载、主题、语言、自适应高度和生命周期控制。宿主不应通过 postMessage 直接修改插件内部 DOM 或任何 VM 状态。双方应使用独立、版本化的消息协议，消息至少包含协议版本、消息类型、会话 ID、序列号、可选请求 ID 和结构化负载。

接收消息时必须：

- 校验 `event.origin`；
- 校验 `event.source` 是否为预期 iframe；
- 使用明确的 `targetOrigin`，不使用 `"*"`（opaque origin 场景按 8.1 的附加控制处理）；
- 校验版本、字段类型、字段范围和消息大小；
- 拒绝未知消息类型；
- 处理重复、乱序和过期消息；
- 限制消息频率；
- 不把宿主声称的“已通过”、分数或最终状态当作权威结果。

**会话动作协议**：VM 动作与公开投影通过认证的 HTTPS / WebSocket 在浏览器与会话编排器之间传输，遵循 6.2 定义的 `ActionRequest` / `ActionResponse` 基线。服务端校验认证上下文、会话绑定、revision、序列号、幂等键、请求大小和频率；拒绝重复、乱序和过期请求。

浏览器断线恢复时，只通过 `get-projection(revision)` 重新同步公开投影，不从服务端下载任何核心状态，也不在本地恢复 VM。

插件还应支持自适应高度、主题和语言配置、静态公开描述包加载、iframe 重载，以及断线重连后从服务端恢复最近公开投影。

### 8.3 题目加载与部署分离

静态加载应优先使用已登记的题目 ID 或 bundle，而不是接受任意 URL；公开描述包发布清单应有内容哈希或签名，并限制响应体、解压后内容、嵌套深度、数组长度和字符串长度。服务端不得根据用户输入直接抓取外部题目 URL，以避免引入 SSRF 和资源耗尽风险。私有判题包从不进入 CDN 或浏览器可达的任何存储路径。

### 8.4 部署分离

规划上将 CTF 平台、VM 插件、会话 API、判题服务和管理后台视为不同的信任域。公开 iframe 不应与管理后台共享高权限 Cookie 或管理端 API；会话编排器和后端 VM Worker 与管理后台分离部署。正式部署需要根据实际来源配置 `frame-ancestors`、CSP、`worker-src`、`connect-src`、`form-action`、HSTS、严格 Referrer Policy 和 Permissions Policy。

## 九、服务端权威判题与安全模型

### 9.1 在线权威会话与最终裁决

浏览器端负责交互、Payload 编辑、公开投影渲染和本地草稿；服务端会话负责所有权威执行。客户端不提交也不被信任的最终内存、寄存器、`RIP`、成功标志或分数。

服务端会话生命周期：

```text
create-session（校验用户、租户、题目权限，绑定 token 与题目版本）
→ action / step / run-to-event / pause（服务端串行执行并返回投影）
→ undo / checkout-checkpoint / reset（服务端恢复状态并重新投影）
→ create-checkpoint（服务端保存快照）
→ sync-projection（断线后重新同步公开投影）
→ submit（引用服务端规范化动作日志）
→ close-session
```

服务端处理流程：

```text
校验用户、租户和题目权限
→ 校验题目版本、会话和动作格式
→ 使用私有题目包和服务端 VM 状态执行动作
→ 检查步数、内存、输入、输出和超时
→ 检查权威目标条件
→ 生成脱敏公开投影并保存审计信息
```

默认只接受原始、结构化且受限的用户动作，由服务端根据已锁定的题目版本自行解析和编译。若未来确实需要接收规范化 IR，IR 必须被视为完全不可信输入，经过独立 Schema、opcode 白名单、操作数范围、区域权限、版本和资源预算的重新校验，不能绕过服务端编译流程直接执行。

正式提交引用服务端会话记录的规范化动作日志；独立 verifier 可以对该日志做最终重放、隐藏测试裁决和审计。这样设计使交互状态与正式裁决分离，支持会话服务重启、任务超时、强制终止和结果可复现。

建议将 API 服务和执行/判题 Worker 分离：

```text
API 服务（会话编排器）
  ├── 认证
  ├── 授权
  ├── 限流
  ├── 请求大小校验
  ├── 会话与 revision / 幂等管理
  └── 投递会话命令
          ↓
会话队列
          ↓
隔离的后端 VM Worker（交互式执行）
          ↓
独立 verifier（提交时最终重放与裁决）
```

执行与判题 Worker 应具备独立进程或容器、最大 CPU 时间、wall-clock 总超时、最大内存、最大执行步数、最大调用栈/状态迁移深度、最大操作序列长度、最大输出和轨迹长度、无网络、无非必要文件系统访问、无子进程创建、可强制终止和最大重试次数。请求体、解析后的题目包、解压内容、checkpoint、snapshot、trace 和日志也必须有大小及嵌套深度限制；容器或操作系统层应使用最小权限、只读文件系统、网络隔离和资源配额。强制终止后必须清理任务状态，避免 Worker 池复用造成跨任务数据残留或重试放大；服务端 Worker 崩溃后由服务端快照替换恢复，浏览器不参与恢复。

建议使用稳定的结果类型，例如 `success`、`wrong_answer`、`invalid_action`、`program_crash`、`memory_fault`、`resource_limit`、`timeout`、`engine_error`、`challenge_invalid`、`replay_mismatch` 和 `cancelled`。对学习者展示有限且有帮助的信息，内部堆栈、文件路径、隐藏测试和宿主异常只进入受控日志。

### 9.2 威胁模型与安全边界

**威胁模型：浏览器完全不可信。** 选手可以：

- 读取浏览器 JS 堆、DOM、前端状态和浏览器 Worker 内存；
- 拦截、修改和重放网络请求；
- 修改或删除 IndexedDB、localStorage 和 Cache Storage；
- 伪造前端成功状态或界面显示；
- 观察消息长度、时序和错误差异。

任何发送到浏览器的数据都应视为可被选手完整读取。所有这些攻击都不应获得服务端秘密或改变最终裁决。有效防线是“隐藏状态根本不下发”，而不是在前端隐藏或混淆。

系统划分为四个安全边界：

1. **浏览器展示边界**：完全不可信。只持有 UI 状态、公开投影、Payload 草稿和短期会话凭证；不持有完整 VM Core、私有题目包和权威快照；
2. **嵌入与协议边界**：iframe、Web Component 和 postMessage 只解决来源、消息和宿主隔离，不是 VM 安全边界；`postMessage` 的来源校验不能替代 API 认证与授权；
3. **后端交互式 VM 边界**：完整 VM Core、完整状态、私有题目包和服务端 seed 均位于后端隔离 Worker / 进程 / 容器；所有用户动作由后端校验和串行执行，只返回公开投影；
4. **后端权威判题边界**：独立 verifier 对服务端规范化动作日志做最终重放、隐藏测试裁决和成绩裁决；隐藏测试和权威目标条件只在此边界内使用。

数据分类：

| 数据类别 | 浏览器可见 | 存储位置 |
|---|---|---|
| 公开描述包 | 是 | CDN / 浏览器 |
| 私有判题包（含隐藏 flag、隐藏测试、完整 IR、seed） | 否 | 仅服务端 |
| 用户动作记录（受限动作请求） | 提交内容可见 | 双方 |
| 私有 VmState、服务端快照、完整事件日志、私有目标条件 | 否 | 仅服务端 |
| 公开投影 / ProjectionDelta | 是 | 服务端生成，浏览器仅缓存 |

禁止发送到浏览器：隐藏 flag、隐藏测试、私有目标条件、私有 capability 返回值、完整 IR、原始快照、完整事件日志、内部堆栈和文件路径。

**侧信道约束**：公开投影、错误反馈、事件和回放不得通过长度、时序、错误差异或调试字段间接暴露服务端秘密。投影采用字段白名单而非黑名单；错误精度按 ProjectionPolicy 粗化；随机秘密需要做投影差分测试。

跨域嵌入到判题 API 时，宿主平台应通过后端签发短期、单用途或有限次数的 embed token，并将租户、用户、题目版本、iframe 会话和过期时间绑定到 token。API 必须从已验证的认证上下文派生租户和用户，不接受请求体或 `postMessage` 中自报的身份；CORS 只允许配置的精确来源。若使用 Cookie，必须配置 CSRF 防护；提交凭证不得使用管理后台凭证或长期 URL 参数。

多租户场景下，用户、题目、题目版本、隐藏测试、提交、判题任务、结果、日志、缓存和对象存储都必须带租户和权限作用域。缓存键、对象路径和数据查询不能只按资源 ID 构造；还需要设置每租户并发、提交频率、CPU、内存和存储预算。

前端禁止右键、混淆代码、检测开发者工具或前端倒计时都**不能**作为真正的反作弊控制。有效控制应放在服务端串行执行、独立重放、隐藏测试、短期提交凭证、状态版本检查、限流和审计日志中。

## 十、前端性能与运行时约束

VM 不在浏览器执行后，性能优化首先解决“投影生成—网络传输—渲染”链路，而不是一开始改写底层：

```text
后端 VM 执行
→ 私有事件生成
→ ProjectionPolicy 白名单与脱敏
→ 序列化与压缩
→ 网络传输
→ 浏览器接收 ProjectionDelta
→ requestAnimationFrame 合帧
→ 局部 DOM / SVG 更新
```

### 10.1 必须遵守的性能原则

1. 后端 VM Worker 持有完整权威状态，浏览器任何位置（主线程、Worker、IndexedDB）都不得持有完整 VM 状态；
2. 主线程只保存公开状态投影和 UI 状态；
3. 不逐条指令发送完整投影；
4. 按教学动作或关键事件返回 `ProjectionDelta`；
5. 服务端维护 dirty range 并合并连续写入后再传输；
6. 使用 `requestAnimationFrame` 合并一帧内的 UI 更新；
7. 只更新变化的内存 cell，不重绘整张内存表；
8. 只有 benchmark 证明必要时，才引入二进制编码或压缩等传输优化；
9. 任何前端优化不得把私有 VM 状态复制到浏览器。

### 10.2 执行与渲染策略

服务端会话命令串行执行，并受指令预算、时间片和资源配额限制；调度时钟只用于控制运行时响应性，不得进入 VM 的可观察语义，从而保证回放确定性。暂停、取消和长循环终止由服务端在批次边界处理。暂停响应和长循环终止应作为验收场景验证。

浏览器 Web Worker 是可选的，只能处理公开投影合并、数据格式转换和渲染辅助，不得运行 VM。断线时浏览器只读展示最近一次收到的公开投影；重连后通过 `sync-projection` 恢复。

提供动作级、事件级和指令级三种模式，均为服务端执行模式。初学者默认使用动作级或事件级执行，指令级调试只在用户主动打开时启用。

字节视图优先使用语义化 DOM；中等规模使用虚拟列表；指针和控制流关系使用 SVG；大规模原始内存再评估 Canvas 或 WebGL。屏幕阅读器需要的信息不能只存在 Canvas 中。

### 10.3 建议的工程目标

以下目标是待 benchmark 和真实网络、真实设备测试确认的工程目标，不代表当前已经达到：

- 动作往返（action RTT）p50 / p95 待真实网络 benchmark 后确定；
- 服务端单步延迟待 benchmark 后确定；
- 暂停请求确认小于 100ms（不含网络往返）；
- 普通 UI 帧更新尽量小于 8ms；
- 主线程长任务尽量小于 50ms；
- 投影传输量按动作粒度控制并持续观测；
- 小题目时间线跳转小于 100ms（服务端 checkpoint 恢复 + 投影同步）；
- 内存视图只更新 changed ranges。

Benchmark 至少覆盖服务端执行、投影与网络传输、UI 渲染和会话恢复四类场景，并比较不同执行步数、内存规模、投影批次、压缩策略和渲染方式。测试环境应包含低端笔记本、普通桌面机、受限 CPU 或节能模式，以及真实公网与弱网条件。

### 10.4 性能模式

三种模式的输出粒度均由服务端控制：

- **教学模式**：解释详细，保留较细公开 diff，支持回退，优先保证可理解性；
- **高速回放模式**：服务端批量执行，减少中间投影，只保留关键 checkpoint；
- **诊断模式**：保留细粒度事件，允许受限导出 trace，用于开发和题目调试。

## 十一、MVP 定义与交付物

### 11.1 MVP 的一个完整闭环

第一版聚焦：**栈帧、缓冲区和返回地址**。

MVP 至少包括：

- 栈内存可视化（公开投影）；
- `RSP`、`RBP`、`RIP`；
- 局部 buffer、saved RBP 和 return address；
- little-endian；
- `write_bytes`；
- `push/pop`；
- `call/ret`；
- 服务端会话执行、单步、回退、checkpoint 和时间线；
- 分级提示和可解释错误（脱敏）；
- JSON 题目格式（公开描述包 + 私有判题包）；
- iframe Demo；
- Web Component；
- 服务端会话 API 与断线恢复；
- 独立 verifier 与审计日志；
- 6—10 道渐进式题目。

MVP 的完成标准是学习者能够打开题目、观察栈帧、构造 payload、通过服务端会话执行受控操作、看到公开投影变化、解释失败原因、请求服务端回退重试并完成一次服务端裁决的提交；同时选手篡改浏览器内存不能获得隐藏关键信息，也不能影响正式成绩。

### 11.2 MVP 暂不交付

除第三节非目标外，以下内容不作为 MVP 验收项：

- 任意脚本或宿主代码执行；
- 真实 ELF、容器和完整 Linux 环境；
- 复杂堆和多架构支持；
- 在线编辑器、AI exploit 和实时协作；
- 浏览器本地权威 VM、离线完整执行或本地判题；
- 未经 benchmark 验证的低层传输优化。

## 十二、开发阶段与里程碑

### 阶段一：冻结信任模型、数据分类和会话协议

交付私有 `VmState`、`PublicStateProjection`、`ProjectionPolicy`、`ActionRequest` / `ActionResponse`、公开/私有题目包 Schema、错误格式、iframe handshake 和版本策略。该阶段确认产品边界、最小 DSL、字段分类规则、秘密零驻留清单和判题安全原则。任何无法证明“秘密不进入浏览器”的字段设计不得进入下一阶段。

### 阶段二：实现后端 VM Core 与会话编排

完成后端内存读写、栈帧、寄存器、`call/ret`、私有目标条件、服务端快照与回放、隔离 Worker、revision 与幂等、资源限制和边界测试。引擎 crate（`vm-core`、`vm-runtime`、`projection`）以 Rust 实现（ADR-8），并满足 safe-Rust 与确定性约束；先以正确性和确定性为主要目标。

### 阶段三：实现投影层与权威 API

完成 ProjectionPolicy、脱敏器、`ProjectionDelta`、认证 WebSocket 通道、断线同步、服务端 COW 快照和规范化动作日志。

### 阶段四：实现教学 UI

完成公开投影渲染、结构视图、字节视图、寄存器、调用栈、Payload 构造器、diff、时间线、checkpoint、提示和错误解释，并验证键盘操作与基础无障碍体验。

### 阶段五：实现 iframe 插件与嵌入安全

完成独立构建产物、postMessage 宿主协议、embed token、自适应高度、主题和语言、静态公开描述包加载、断线重连和错误恢复。

### 阶段六：接入独立判题并依据教学反馈扩展

完成 verifier 重放规范化动作日志、隐藏测试裁决、审计日志、租户隔离和限流。在前述闭环稳定后，再评估堆、ROP、防护机制、信息泄露、更完整指令集、后端 WASM 或真实 ELF 实验模式。是否扩展以及优先级由实际教学数据、性能基准和安全评审共同决定。

## 十三、测试、质量保障与验收

### 13.1 VM Core 测试

覆盖地址读写、越界访问、不可写和不可执行区域、little-endian、栈帧创建和销毁、`push/pop`、`call/ret`、`leave`、archBits 位宽掩蔽（32/64 两种位宽下的算术、移位与出界行为）、自定义指令解释器（直线语义、恒定步数）、作者接口派发（`syscall`/`call`，效果原语封闭集）、Canary、reset、checkpoint、快照恢复、事件重放一致性、随机 seed 确定性、超时、指令预算和服务端 Worker 崩溃后的快照替换恢复。

Rust 引擎侧补充覆盖：cargo miri 无未定义行为、题目包与动作解析器 fuzz 无 panic、同引擎跨平台（x86-64 / ARM64）与 debug / release 结果一致、整数溢出检查触发时按 `engine_error` 安全终止而非静默回绕。

VM Core 只能从后端构建目标中加载；浏览器构建不得包含 VM 执行模块。

### 13.2 DSL 与题目包测试

覆盖 Schema 校验、版本迁移、未定义引用、地址重叠、不可达目标、循环和深度限制、过大的内存和字符串、隐藏区域意外公开、恶意嵌套结构、重复键和类型混淆。题目发布前运行参考解、边界输入和回归测试。

字段分类检查器覆盖：架构位宽（32 位题目初值/立即数越界拒绝）、VMA 4KB 倍数对齐（区域大小与页大小）、寄存器声明面（必选核心寄存器缺失拒绝、一般命名落入 `FLAG` 保留区拒绝、自定义命名通过、超上限拒绝）、opcode v2（`read`/`write` 拒绝、`leave` 依赖 `RBP`）、`syscall`/`call` 引用未声明接口拒绝、自定义指令语义含控制转移拒绝、自定义指令/接口 `displayText` 携带谓词信息或隐藏区域名拒绝。

额外覆盖：公开描述包与私有判题包的字段集合严格分离；公开包不能通过默认值、引用 ID 或 Schema 元数据推导私有字段；编译 IR 不进入浏览器构建；私有 capability 不出现在公开 Schema、错误和 trace 中。

### 13.3 插件协议和判题测试

覆盖 handshake 超时、重复消息、消息乱序、非法序列号、不受信任来源、iframe 重载、宿主不支持能力、过期 revision、重复幂等键、跨租户 session、断线重连与投影重同步、服务端重放一致性、权限校验、限流、超时和资源限制。

### 13.4 UI、无障碍和部署测试

至少覆盖 320、375、768、1024、1440 和 1920 宽度；Chrome、Firefox 和 Safari；主题切换、键盘操作、reduced-motion、高对比度、非根路径部署、受限 CSP。网络中断时：浏览器展示最近一次公开投影并暂停需要服务端的动作，恢复后重新同步；不得降级到本地 VM 执行。自动化无障碍检查不能替代键盘和屏幕阅读器抽样验证。

### 13.5 秘密零驻留与侧信道测试

- 构建产物检查：前端 bundle、SourceMap、静态资源和网络响应中不存在隐藏 flag、隐藏测试、完整 IR、私有题目包、权威快照和服务端 seed；
- 运行时检查：浏览器主线程、Worker 内存、IndexedDB、localStorage、Cache Storage 和 WebSocket 帧中秘密零命中；
- 投影泄漏检查：字段白名单校验、随机秘密差分测试、响应长度/事件数量/错误分类/执行时序与秘密无相关性；
- 客户端篡改检查：篡改前端状态、伪造投影、重放旧请求、伪造成功标志均不影响服务端权威状态和正式成绩。

### 13.6 计划书层面的验收标准

MVP 验收应同时满足：

- 原始产品定位、教学动机、Web 插件形态和框架化扩展方向没有被削弱；
- 至少一条完整的“输入字节到目标条件”的教学闭环可以演示；
- 题目可以通过受限格式加载、校验和版本化，公开/私有双包字段分离经过检查；
- 浏览器只持有公开投影，服务端持有全部权威状态和裁决职责；
- 失败结果能够解释，而不是只返回通用错误；
- 关键状态可以单步、回退和重放（服务端会话能力）；
- 运行时、插件协议、会话边界和秘密零驻留有对应测试；
- 性能数字经过目标网络和设备 benchmark 后再确定是否达标。

## 十四、风险、取舍与应对措施

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 范围膨胀为完整 CPU/OS 模拟器 | 延迟 MVP，增加安全和测试成本 | 固定栈帧、buffer、return address 闭环，复杂能力后置 |
| 原文定位被技术细节稀释 | 产品目标失焦 | 所有技术章节回扣初学者教学因果链 |
| DSL 逃逸到宿主环境 | 可能造成代码执行或数据访问风险 | Schema、静态检查、受限 IR、白名单 Runtime 和资源预算 |
| 公开投影过度暴露 | 通过长度、时序或错误差异间接泄露隐藏状态 | 字段白名单、错误粗化、差分测试和侧信道审查 |
| 客户端篡改状态或成绩 | 正式成绩不可信 | 服务端串行执行并独立裁决；浏览器只接收脱敏投影，篡改无法获得秘密或影响成绩 |
| 服务端容量或可用性不足 | 会话排队、动作延迟上升 | 会话配额、公平调度、容量监控和降级策略 |
| 会话状态不一致 | 回退、重放和提交争议 | revision、幂等键、服务端快照和一致性测试 |
| 网络延迟影响教学体验 | 动作反馈慢，初学者困惑 | ProjectionDelta 增量、压缩、批处理和乐观 UI（乐观状态明确标记为待服务端确认） |
| iframe 与跨域策略不兼容 | 平台接入失败 | 独立来源、版本化协议、明确 origin 校验和接入 Demo |
| 回放不确定 | 争议无法复现，题目升级可能改变结果 | 服务端固定 seed，记录题目/引擎/Profile/判题版本和状态哈希 |
| 过早引入 WASM 等低层优化 | 增加复杂度但收益不确定 | 先完成 Rust 引擎正确实现并建立 benchmark 基线，以 benchmark 驱动优化 |
| Rust 人才与维护风险 | 引擎迭代放缓、贡献门槛升高 | 引擎锁定为无 async、无 unsafe 的纯状态机 crate；协议保持 JSON Schema 化与 golden fixture 纪律，保留 TypeScript vm-core 回退路线（ADR-8） |
| TS 与 Rust 契约漂移 | 动作、投影或 IR 解析不一致 | JSON Schema 单一来源、golden fixture 往返测试与跨平台确定性差分测试 |
| 提示直接给出答案 | 学习者缺少独立分析过程 | 采用四级提示，不自动修正关键偏移和端序 |
| 低端设备性能不足 | 初学者体验不稳定 | 增量投影、虚拟列表、降级策略和真实设备测试 |
| 题目质量不一致 | 学习路径断裂 | 发布前参考解、边界输入、题目回归和课程审核 |

## 十五、成功指标与后续运营观察

项目上线或试用后，建议观察以下指标，而不是只统计提交次数：

- 学习者从打开题目到首次成功的时间；
- 各题完成率和放弃率；
- 提示使用等级和回退次数；
- 错误类型分布及重复错误比例；
- 学习前后对地址、栈帧、端序和控制流的概念理解变化；
- 动作请求 p50 / p95 延迟和断线恢复成功率；
- 单会话服务端执行延迟和并发会话数；
- 投影传输量；
- 从插件加载到可交互的时间；
- CTF 平台接入所需时间；
- 出题人制作、校验和调试一题所需时间；
- 低端设备上的投影渲染、内存占用和断线重连性能；
- 服务端裁决失败、协议错误和题目配置错误数量。

这些指标用于验证“提升新生水平与兴趣”的目标，并决定是否进入高级能力扩展，而不是把尚未验证的数字写成既定承诺。

## 十六、四条必须坚持的底线

1. **VM Core、完整状态和隐藏判题信息完全隔离在后端。**
2. **浏览器只接收可公开的脱敏投影，不负责最终计分或权威状态保存。**
3. **服务端会话串行执行所有动作，单步、回退、checkpoint、回放和最终裁决均以服务端为准。**
4. **题目 DSL 不执行任意宿主代码，默认使用独立来源 iframe，并保持 Core、UI、协议和平台适配层解耦。**

这四条底线同时是安全边界、架构边界和后续可扩展性的基础。
