# StackMaster 项目计划书

## 产品定位

一个可嵌入、可回放、可解释的 Pwn 概念实验室，而不是浏览器中的完整 Linux 或 x86 模拟器。

由于 AI 的冲击，在 CTF 新生赛中放一些经典的题目的必要性已经丧失，且难以让新生获得学习的正向反馈，所以我们需要一些新的手段去更好的反映、提升新生的水平与兴趣。

因此，该项目将通过一个将内存可视化展现出来的 vm ，让新生通过指定的操作方式直接操作内存来解决 vm 中的谜题来学习 pwn 的基础知识。同时为了方便各靶场引入该项目，项目将以 Web 插件的形式去实现。

同时为了具备更好的可拓展性，项目将允许出题人更加方便地去修改虚拟指令集、方法、寄存器和内存布局，这意味着项目将具备一定程度的框架属性。

---

## 一、项目背景与建设动因

### 1.1 要解决的问题

本项目不是简单地把传统 Pwn 题目搬到浏览器中，而是针对初学者在入门阶段遇到的三个问题提供过渡性的实验环境：

1. **抽象关系难以观察**：内存地址、字节、栈帧、寄存器和控制流之间存在因果关系，但传统终端交互通常只呈现输入、输出或错误结果。
2. **错误反馈不足**：学习者可能只能看到“成功”或 `Segmentation fault`，难以知道是哪一次写入覆盖了哪个对象，也难以理解 `ret` 如何改变 `RIP`。
3. **平台接入成本较高**：不同靶场和教学平台需要重复实现交互界面、题目加载和状态展示，题目作者也缺少一套可控的扩展模型。

项目的价值不是替代传统 Pwn 环境，而是让学习者先建立可迁移的心智模型，再逐步进入真实二进制、调试器和 CTF 题目。

### 1.2 核心教学因果链

所有第一阶段功能都应服务于以下学习链路：

```text
输入字节
→ 覆盖内存
→ 修改栈帧或数据
→ 影响寄存器
→ 改变控制流
→ 满足目标条件
```

这条因果链是项目区别于普通在线判题系统的核心。系统不仅要告诉学习者结果，还要展示结果是如何由每一步状态变化产生的。

### 1.3 项目愿景

建设一个面向 Pwn 入门教学的可嵌入实验框架，使：

- 初学者能够观察、操作、回退并解释一次 Pwn 概念实验；
- 出题人能够通过受约束的题目配置定义内存布局、指令、寄存器、操作和目标条件；
- CTF 平台能够以低接入成本嵌入实验，并把正式判题交给可信的服务端；
- VM Core、教学 UI、嵌入协议和平台适配层可以独立演进。

## 二、目标用户与使用场景

### 2.1 Pwn 初学者与新生

主要需求：

- 认识地址、字节、十六进制、端序和基本寄存器；
- 观察 buffer、saved RBP、return address 等语义对象；
- 通过指定操作构造 payload，而不是直接得到答案；
- 单步执行、查看 diff、获得分级提示并回退重试；
- 从可视化实验逐步过渡到真实 Pwn 题目。

### 2.2 出题人和课程设计者

主要需求：

- 配置虚拟内存区域、寄存器和教学对象；
- 选择或定义受白名单约束的操作；
- 声明成功条件、失败条件和资源限制；
- 编写分级提示，控制提示信息逐步增加；
- 通过题目包和版本机制维护多道渐进式题目；
- 使用参考解、边界输入和回放结果验证题目质量。

### 2.3 CTF 平台维护者

主要需求：

- 在静态 HTML、CTFd、Vue、Angular、Django 模板或自建平台中接入；
- 不强制宿主安装特定前端框架；
- 允许插件独立发布、升级、回滚和故障恢复；
- 通过服务端接口完成正式提交和成绩裁决；
- 对平台来源、租户和权限进行隔离。

## 三、产品范围、边界与非目标

### 3.1 产品范围

本项目建设的是一个**可视化内存 VM 教学和题目框架**，包括：

- 受限的 VM 状态和操作模型；
- 内存、寄存器、栈帧和控制流的可视化；
- Payload 构造、单步、回退、checkpoint、回放和错误解释；
- 声明式题目格式与出题人扩展机制；
- 可嵌入不同 CTF 平台的 Web 插件；
- 服务端可重放的权威判题接口。

### 3.2 明确的非目标

MVP 阶段不追求把项目做成完整 CPU 或操作系统模拟器，因此暂不包括：

- 完整 x86-64 指令集；
- ELF 加载器和任意 ELF 上传；
- 完整 Linux、真实 shellcode 或任意 C/Python/JavaScript 执行；
- 完整 glibc、真实容器或任意系统调用；
- 复杂堆分配器、多架构兼容；
- 在线题目编辑器；
- AI 自动生成 exploit；
- 多人实时协作、排行榜和其他未服务于首个教学闭环的功能。

后续是否加入 ASLR、PIE、Canary、NX、信息泄露、格式化字符串、堆和 UAF，应依据教学反馈和实现验证分阶段决定，而不是在 MVP 阶段一次性承诺。

## 四、教学闭环与核心功能

### 4.1 学习者使用流程

```text
观察内存布局
→ 构造 Payload
→ 执行指定操作
→ 查看内存、寄存器和控制流变化
→ 获得错误解释或分级提示
→ 回退到检查点
→ 调整 Payload
→ 重放并提交
```

系统应允许学习者在理解过程中保留试错记录，而不是只保留最后一次提交。

### 4.2 内存和执行状态可视化

至少提供以下面板：

- 题目目标、当前概念、执行步数和提示等级；
- 结构化内存视图，展示代码区、全局区、堆区、栈区、输入区和关键对象；
- 字节视图，展示地址、十六进制字节、ASCII 和语义归属；
- 寄存器面板，重点展示 `RSP`、`RBP`、`RIP` 以及题目使用的通用寄存器；
- 调用栈和控制流变化；
- 当前状态与上一次状态的 diff；
- Payload 构造器和最终字节偏移。

结构视图和字节视图必须联动：点击 `return address` 时高亮对应字节，点击 payload 字节时显示其覆盖的对象；颜色和文本应区分用户输入、程序写入和初始数据。

### 4.3 Payload 构造器

Payload 不应只通过一个黑色终端输入框输入。可提供以下字节块：

- 填充，例如 `A × 40`；
- 原始字符串；
- 整数值；
- 地址；
- 空字节；
- 已编码字节。

每个字节块应显示逻辑值、实际字节、长度、端序和在最终 payload 中的偏移。系统可以提供辅助解释，但不应默认替学习者计算所有关键偏移或自动修正端序。

### 4.4 执行、回退和反馈

支持以下执行粒度：

| 模式 | 用途 |
|---|---|
| 运行到结果 | 快速验证题目是否完成 |
| 执行到关键事件 | 在 `read`、`write`、`call`、`ret` 或异常处暂停 |
| 单条机器动作 | 理解寄存器和控制流变化 |
| 单字节 diff | 排查 payload 覆盖范围 |

必须支持运行、暂停、单步、上一步、重置、创建 checkpoint、时间线拖动和回放。

错误反馈不应只显示：

```text
Segmentation fault
```

而应解释：读取或写入发生在哪个地址、该值被如何解释、为什么不在可执行或可写区域，并提示学习者检查 padding、little-endian 和 `RSP` 位置。错误类型至少覆盖输入格式错误、payload 长度错误、偏移不足或过长、端序错误、权限错误、非法 `RIP`、Canary 破坏、参数寄存器错误以及目标条件未满足。

提示采用逐级增加信息的方式，例如：

```text
Hint 1：观察 RBP 和 RSP。
Hint 2：找出 buffer 与 return address 的距离。
Hint 3：计算需要填充的字节数。
Hint 4：检查目标地址的 little-endian 表示。
```

## 五、总体技术架构

### 5.1 分层架构

```text
CTF 平台
   │
   │ iframe / Web Component / postMessage
   ▼
插件 Shell
   ├── 题目加载器
   ├── 可视化 UI
   ├── 嵌入协议
   └── 本地进度
          │
          ▼
Web Worker
   └── VM Runtime
          │
          ▼
纯 TypeScript VM Core
   ├── Virtual Memory
   ├── Registers
   ├── Stack / Heap
   ├── Call Frames
   ├── Operation Interpreter
   ├── Goal Evaluator
   └── Replay / Snapshot
```

建议按职责拆分为以下模块：

- `vm-core`：不依赖 DOM、Lit、React、iframe 或 Node.js 的纯 VM；
- `challenge-schema`：JSON Schema、公共类型和校验器；
- `challenge-compiler`：将题目 DSL 编译为受限 IR；
- `vm-ui`：内存、寄存器、调用栈、时间线和反馈 UI；
- `embed-runtime`：iframe 和 `postMessage` 协议；
- `web-component`：原生 `<pwn-memory-vm>` 自定义元素；
- `react-wrapper`：可选的 React 薄包装器；
- `verifier`：服务端重放和判题。

**VM Core 不应该知道自己运行在 Lit、React、iframe 还是 Node.js 中。**

### 5.2 技术选型

| 领域 | 首选方案 | 计划中的作用 |
|---|---|---|
| 核心语言 | TypeScript | 浏览器、Worker、Node.js 和插件 SDK 共享类型 |
| UI 组件 | Lit + Web Components | 提供框架无关的嵌入接口 |
| 构建工具 | Vite | 构建库、Worker 和静态插件产物 |
| VM 执行线程 | Web Worker | 将 VM 执行与 UI 渲染隔离 |
| 题目格式 | JSON + JSON Schema | 题目可校验、可版本化、可跨语言实现 |
| 运行时校验 | Ajv；内部可辅以 Zod | 校验公开题目包和 TypeScript 内部边界 |
| 本地状态 | IndexedDB | 保存离线进度、checkpoint 和回放数据 |
| 单元/属性测试 | Vitest + fast-check | 覆盖状态转换、边界和回放一致性 |
| E2E 测试 | Playwright | 覆盖嵌入、交互和关键学习流程 |
| 无障碍测试 | axe-core | 辅助检查键盘和 WCAG 基础问题 |
| 服务端判题 | Node.js + Fastify 或 FastAPI | 接收提交并交给独立 Worker 重放 |

React 和 Vue 可以提供薄包装器，但不作为主插件接口。项目的主要跨平台接口优先选择原生 Web Component；默认的跨域分发形态优先选择独立来源 iframe。

## 六、VM 语义与状态模型

### 6.1 MVP 的虚拟硬件

MVP 重点模拟以下内存区域：

- 代码区；
- 全局区；
- 堆区；
- 栈区；
- 输入区；
- 题目定义的关键区。

寄存器至少包括：

- `RSP`、`RBP`、`RIP`；
- `RAX`、`RBX`、`RCX`；
- `RDI`、`RSI`、`RDX`；
- 题目需要的部分 FLAG。

MVP 可以支持 `push`、`pop`、`mov`、基本算术与位运算、有限跳转、`call`、`ret` 以及教学化的 `read`、`write`。MVP 的操作不要求等同于完整机器指令，应优先服务于概念解释。

### 6.2 统一状态转换

所有状态变化必须经过统一入口：

```text
用户操作
→ 边界校验
→ VM 状态转换
→ 结构化事件
→ 公开状态投影
→ 目标条件检查
```

核心状态至少包括寄存器、虚拟内存、调用栈帧、指令指针、事件日志、运行时约束和运行状态（如 `running`、`paused`、`won`、`failed`）。UI 不得直接修改 VM 内存对象。

地址和 64 位值在 VM Core 中优先使用 `bigint`，题目 DSL 和公开 API 使用明确的十六进制字符串。展示层负责转换，同时明确溢出、符号扩展、移位、端序和权限行为。

### 6.3 确定性与可回放

回放应采用“事件日志 + 周期性快照”，而不是只保存最终状态或保存无限增长的事件流。每次操作至少记录操作类型和参数、前后状态哈希、内存与寄存器变化、事件序号、题目版本、VM Profile 和引擎版本。

回放不得依赖当前时间、浏览器随机数、网络响应顺序、宿主线程调度或浏览器未定义行为。题目需要随机化时，应使用可复现的 seed，并将 seed 策略和运行环境版本写入回放信息。

内存建议按固定大小分页，并在后续实现中采用 Copy-on-Write 快照，避免每一步复制完整 VM 状态。

## 七、题目 DSL 与出题人扩展机制

### 7.1 题目发布流程

出题人扩展能力必须是受控的框架能力，而不是任意代码执行能力。公开题目包只包含浏览器教学所需的状态、布局、操作说明和非权威反馈条件；私有判题包只由服务端持有，包含隐藏 flag、隐藏测试和权威目标条件。建议流程为：

```text
作者 DSL
  → JSON Schema 校验
  → 静态检查
  → 编译为受限 IR
  → 白名单 Runtime 执行
```

题目包可包含：

- 元数据和题目版本；
- VM Profile；
- 初始内存和初始寄存器；
- 教学对象；
- 允许操作和操作参数；
- 步数、写入次数、输入长度等资源限制；
- 提示阶梯和 checkpoint；
- 成功条件和失败条件。

### 7.2 可扩展内容

在版本和安全约束下，出题人可以配置或组合：

- 虚拟指令集或允许的操作；
- 方法、调用机制和操作注册表；
- 寄存器集合及其展示语义；
- 代码、全局、堆、栈、输入和关键区域的内存布局；
- 教学对象、引用关系和可视化标签；
- 成功、失败和资源限制条件；
- 多阶段题目的有限状态机。

这里的“扩展”仅指选择固定 Runtime 中经过审计的内置 opcode、predicate 和操作 ID，并配置其受 Schema 约束的参数；题目包不得动态注册处理函数、加载模块或注入新的执行代码。若未来新增指令语义，应作为经过审核、测试和版本化的 Runtime 发布，而不是随题目包运行时加载。

多阶段题目中的每个状态应包含允许操作、前置条件、迁移条件、有限副作用、失败条件和资源预算。循环必须有静态上限或动态指令预算。

### 7.3 DSL 的安全边界

客户端题目包只能包含教学所需的公开状态；隐藏 flag、隐藏测试、私有目标条件和服务端判题秘密只能存在服务端。客户端的目标评估器只能负责非权威的公开反馈；例如 `virtual_file:flag` 一类 capability 若保留，应明确为服务端专用，不得出现在客户端题目包或公开回放中。

题目 DSL 不设计成脚本语言，不允许：

- JavaScript、Python、Lua 等任意回调；
- `eval`、`Function` 或动态导入；
- 用户自定义函数和任意 WebAssembly；
- 文件系统、网络、进程和宿主对象访问；
- 无限循环、无限递归和动态拼接 capability 名称。

表达式只支持常量、只读寄存器引用、命名内存区域查询、有界整数和位运算、比较、布尔组合、固定长度切片、有界字节匹配及枚举值比较。复杂逻辑优先沉淀为经过审计的内置谓词。

### 7.4 版本管理

至少区分以下版本：

1. DSL Schema Version；
2. VM Engine Version；
3. VM Profile Version；
4. Challenge Content Version。

正式判题和回放还应记录题目包哈希、VM Profile 哈希、引擎构建 ID、判题规则版本、随机种子策略和规范化提交内容哈希。生产环境不得自动使用“最新引擎”，正式题目应锁定执行环境。

## 八、插件嵌入、协议与部署

### 8.1 默认嵌入形态

默认采用跨域、独立来源的 iframe：

- 宿主平台不需要安装前端依赖；
- 避免宿主 CSS 污染插件；
- 插件可以独立发布、升级和回滚；
- 兼容不同语言和前端框架；
- 插件异常时较少影响宿主页面。

iframe 应使用最小化的 `sandbox` 权限，并谨慎处理 `allow-same-origin`；不应把长期凭证放入 iframe URL。推荐的独立来源方案应保持插件来源与宿主不同，并由稳定的插件来源配合严格的 `event.origin`、`event.source` 和 `targetOrigin` 校验；不要在与宿主同源的 iframe 中同时使用 `allow-scripts allow-same-origin`。如果采用不带 `allow-same-origin` 的 opaque origin sandbox，则不能仅凭 `event.origin` 为 `"null"` 信任消息；向 opaque origin 发送消息时可能必须使用 `targetOrigin: "*"`，但必须同时依赖预期的 `event.source`、一次性不可预测的握手值、会话绑定、消息认证、序列号和重放校验，或在握手后转移到经过绑定的 `MessageChannel`，不能把 `"*"` 作为唯一信任控制。独立来源 iframe 主要隔离宿主页面，不等于 iframe 内代码或浏览器 Worker 可以被信任，也不能替代服务端安全边界。

同组织、同源或明确可信的平台可以使用 Web Component，但必须明确：**Shadow DOM 和 Web Component 不是安全边界。** 题目包或插件代码不可信时，仍应使用独立来源 iframe。

### 8.2 `postMessage` 协议

宿主不应直接修改 iframe 内部 DOM 或 VM 状态。双方应使用独立、版本化的消息协议，消息至少包含协议版本、消息类型、会话 ID、序列号、可选请求 ID 和结构化负载。

接收消息时必须：

- 校验 `event.origin`；
- 校验 `event.source` 是否为预期 iframe；
- 使用明确的 `targetOrigin`，不使用 `"*"`；
- 校验版本、字段类型、字段范围和消息大小；
- 拒绝未知消息类型；
- 处理重复、乱序和过期消息；
- 限制消息频率；
- 不把宿主声称的“已通过”、分数或最终状态当作权威结果。

插件还应支持自适应高度、主题和语言配置、静态题目加载、iframe 重载，以及 Worker 重启后从最近 checkpoint 恢复。

### 8.3 题目加载与部署分离

静态题目加载应优先使用已登记的题目 ID 或 bundle，而不是接受任意 URL；题目发布清单应有内容哈希或签名，并限制响应体、解压后内容、嵌套深度、数组长度和字符串长度。服务端不得根据用户输入直接抓取外部题目 URL，以避免引入 SSRF 和资源耗尽风险。

### 8.4 部署分离

规划上将 CTF 平台、VM 插件、判题 API 和管理后台视为不同的信任域。公开 iframe 不应与管理后台共享高权限 Cookie 或管理端 API。正式部署需要根据实际来源配置 `frame-ancestors`、CSP、`worker-src`、`connect-src`、`form-action`、HSTS、严格 Referrer Policy 和 Permissions Policy。

---

## 九、服务端权威判题与安全模型

### 9.1 客户端与服务端职责

浏览器端负责交互、即时反馈、可视化和本地回放；服务端负责正式判题和成绩裁决。客户端不提交也不被信任的最终内存、寄存器、`RIP`、成功标志或分数。

服务端处理流程：

```text
校验用户、租户和题目权限
→ 校验题目版本和提交格式
→ 使用相同初始状态和 seed 重放操作
→ 检查步数、内存、输入、输出和超时
→ 判断成功条件
→ 保存结果、状态哈希、版本和审计信息
```

默认只接受原始、结构化且受限的用户动作，由服务端根据已锁定的题目版本自行解析和编译。若未来确实需要接收规范化 IR，IR 必须被视为完全不可信输入，经过独立 Schema、opcode 白名单、操作数范围、区域权限、版本和资源预算的重新校验，不能绕过服务端编译流程直接执行。

建议将 API 服务和判题 Worker 分离：

```text
API 服务
  ├── 认证
  ├── 授权
  ├── 限流
  ├── 请求大小校验
  └── 投递任务
          ↓
判题队列
          ↓
独立判题 Worker
```

判题 Worker 应具备独立进程或容器、最大 CPU 时间、wall-clock 总超时、最大内存、最大执行步数、最大调用栈/状态迁移深度、最大操作序列长度、最大输出和轨迹长度、无网络、无非必要文件系统访问、无子进程创建、可强制终止和最大重试次数。请求体、解析后的题目包、解压内容、checkpoint、snapshot、trace 和日志也必须有大小及嵌套深度限制；容器或操作系统层应使用最小权限、只读文件系统、网络隔离和资源配额。强制终止后必须清理任务状态，避免 Worker 池复用造成跨任务数据残留或重试放大。

建议使用稳定的结果类型，例如 `success`、`wrong_answer`、`invalid_action`、`program_crash`、`memory_fault`、`resource_limit`、`timeout`、`engine_error`、`challenge_invalid`、`replay_mismatch` 和 `cancelled`。对学习者展示有限且有帮助的信息，内部堆栈、文件路径、隐藏测试和宿主异常只进入受控日志。

### 9.2 三个安全边界

1. **浏览器可视化层**：只负责交互、动画和预览，默认视为可被篡改；浏览器 Worker 只提供线程与性能隔离，不是进程级安全沙箱；公开事件、错误反馈、快照和回放不得通过长度、时序或调试字段间接暴露服务端秘密；
2. **受限 DSL/VM 执行层**：只执行有限指令和状态迁移，具有明确资源预算；
3. **服务端权威判题层**：独立重放并保存正式结果。

客户端题目包只能包含教学所需的公开状态；隐藏 flag、隐藏测试、私有目标条件和服务端判题秘密只能存在服务端。客户端的目标评估器只能负责非权威的公开反馈，公开投影、事件和回放不得包含隐藏区域或私有 capability 的返回值。

跨域嵌入到判题 API 时，宿主平台应通过后端签发短期、单用途或有限次数的 embed token，并将租户、用户、题目版本、iframe 会话和过期时间绑定到 token。API 必须从已验证的认证上下文派生租户和用户，不接受请求体或 `postMessage` 中自报的身份；CORS 只允许配置的精确来源。若使用 Cookie，必须配置 CSRF 防护；提交凭证不得使用管理后台凭证或长期 URL 参数。`postMessage` 的来源校验不能替代 API 认证与授权。

多租户场景下，用户、题目、题目版本、隐藏测试、提交、判题任务、结果、日志、缓存和对象存储都必须带租户和权限作用域。缓存键、对象路径和数据查询不能只按资源 ID 构造；还需要设置每租户并发、提交频率、CPU、内存和存储预算。

前端禁止右键、混淆代码、检测开发者工具或前端倒计时都不能作为真正的反作弊控制。有效控制应放在服务端重放、隐藏测试、短期提交凭证、状态版本检查、限流和审计日志中。

## 十、前端性能与运行时约束

性能优化首先解决“执行—通信—渲染”链路，而不是一开始改写 VM 底层：

```text
VM 执行
→ 事件生成
→ Worker 与主线程通信
→ 数据复制
→ UI 更新
→ 布局、绘制和垃圾回收
```

### 10.1 必须遵守的性能原则

1. Worker 持有完整 VM 权威状态；
2. 主线程只保存公开状态投影和 UI 状态；
3. 不逐条指令发送完整状态；
4. 按教学动作或关键事件批量发送 `VmDelta`；
5. 使用 dirty page 和连续写入合并减少传输；
6. 使用 `requestAnimationFrame` 合并一帧内的 UI 更新；
7. 只更新变化的内存 cell，不重绘整张内存表；
8. 先使用可读、正确的 TypeScript 和 BigInt 实现；
9. 只有 benchmark 证明必要时，才引入更低层的数据表示、Transferable、SharedArrayBuffer 或 WASM。

### 10.2 执行与渲染策略

Worker 执行循环必须同时受指令预算和时间片限制；每批执行结束后主动让出控制权，并在批次边界检查暂停、终止和 Worker 重启请求。调度时钟只用于控制运行时响应性，不得进入 VM 的可观察语义，从而保证回放确定性。暂停响应和长循环终止应作为验收场景验证。

提供动作级、事件级和指令级三种模式。初学者默认使用动作级或事件级执行，指令级调试只在用户主动打开时启用。

内存按逻辑区域和分页组织，避免按完整 64 位地址空间分配物理内存。MVP 的小规模内存可以使用区域级 `Uint8Array`；需要回放和较大状态时采用分页、按需加载和 Copy-on-Write。

字节视图优先使用语义化 DOM；中等规模使用虚拟列表；指针和控制流关系使用 SVG；大规模原始内存再评估 Canvas 或 WebGL。屏幕阅读器需要的信息不能只存在 Canvas 中。

### 10.3 建议的工程目标

以下目标来自性能设计文档，是待 benchmark 和真实设备测试确认的工程目标，不代表当前已经达到：

- 主线程长任务尽量小于 50ms；
- 普通 UI 帧更新尽量小于 8ms；
- 暂停按钮响应小于 100ms；
- 普通 Worker batch 约为 1—4ms；
- 高速执行每帧最多一次 UI 更新；
- 小题目回放跳转小于 100ms；
- 内存视图只更新 changed ranges。

Benchmark 至少覆盖 VM 指令、事件通信、UI 渲染和回放四类场景，并比较不同执行步数、内存规模、消息批次、快照策略和渲染方式。测试设备应包含低端笔记本、普通桌面机及受限 CPU 或节能模式环境。

### 10.4 性能模式

- **教学模式**：解释详细，保留较细 diff，支持回退，优先保证可理解性；
- **高速回放模式**：批量执行，减少中间事件，只保留关键 checkpoint；
- **诊断模式**：保留细粒度事件，允许导出 trace，用于开发和题目调试。

## 十一、课程路线与题库规划

建议按照知识点和状态变化组织题目：

```text
Level 0  地址、字节、十六进制
Level 1  栈帧和局部变量
Level 2  小端序
Level 3  覆盖相邻变量
Level 4  找到返回地址偏移
Level 5  ret2win
Level 6  调用约定和 RDI
Level 7  简化 ROP
Level 8  NX、Canary、PIE、ASLR
Level 9  信息泄露
Level 10 格式化字符串
Level 11 堆和 UAF
```

题目设计遵循：

> 每道题只引入一个主要新概念，最多复习一个旧概念。

初始题目可以使用固定地址；学习者理解覆盖和控制流后，再引入 ASLR、PIE、Canary 和 NX。每道题发布前应明确前置知识、观察对象、允许操作、目标条件、常见错误、提示阶梯和参考解。

## 十二、MVP 定义与交付物

### 12.1 MVP 的一个完整闭环

第一版聚焦：**栈帧、缓冲区和返回地址**。

MVP 至少包括：

- 栈内存可视化；
- `RSP`、`RBP`、`RIP`；
- 局部 buffer、saved RBP 和 return address；
- little-endian；
- `write_bytes`；
- `push/pop`；
- `call/ret`；
- 单步执行、回退、checkpoint 和时间线；
- 分级提示和可解释错误；
- JSON 题目格式；
- iframe Demo；
- Web Component；
- 服务端重放接口；
- 6—10 道渐进式题目。

MVP 的完成标准是学习者能够打开题目、观察栈帧、构造 payload、执行受控操作、看到状态变化、解释失败原因、回退重试并完成一次服务端可重放的提交。

### 12.2 MVP 暂不交付

除第三节非目标外，以下内容不作为 MVP 验收项：

- 任意脚本或宿主代码执行；
- 真实 ELF、容器和完整 Linux 环境；
- 复杂堆和多架构支持；
- 在线编辑器、AI exploit 和实时协作；
- 未经 benchmark 验证的 WASM 或 SharedArrayBuffer 优化。

## 十三、开发阶段与里程碑

### 阶段一：冻结协议和语义

交付 `VmState`、`Operation`、`VmEvent`、snapshot/replay 格式、Challenge Schema、错误格式、iframe handshake 和版本策略。该阶段确认产品边界、最小 DSL 和判题安全原则。

### 阶段二：实现纯 VM Core

完成内存读写、栈帧、寄存器、`call/ret`、成功和失败条件、回放及边界测试。先以正确性和确定性为主要目标。

### 阶段三：实现教学 UI

完成结构视图、字节视图、寄存器、调用栈、Payload 构造器、diff、时间线、checkpoint、提示和错误解释，并验证键盘操作与基础无障碍体验。

### 阶段四：实现 iframe 插件

完成独立构建产物、`postMessage`、自适应高度、主题和语言、静态题目加载、Worker 重启和错误恢复。

### 阶段五：接入服务端判题

完成认证、授权、租户隔离、限流、判题队列、独立 Worker、服务端重放和审计日志。

### 阶段六：依据教学反馈扩展

在前述闭环稳定后，再评估堆、ROP、防护机制、信息泄露、更完整指令集、WASM 或真实 ELF 实验模式。是否扩展以及优先级由实际教学数据、性能基准和安全评审共同决定。

---

## 十四、测试、质量保障与验收

### 14.1 VM Core 测试

覆盖地址读写、越界访问、不可写和不可执行区域、little-endian、栈帧创建和销毁、`push/pop`、`call/ret`、Canary、reset、checkpoint、快照恢复、事件重放一致性、随机 seed 确定性、超时、指令预算和 Worker 崩溃恢复。

### 14.2 DSL 与题目包测试

覆盖 Schema 校验、版本迁移、未定义引用、地址重叠、不可达目标、循环和深度限制、过大的内存和字符串、隐藏区域意外公开、恶意嵌套结构、重复键和类型混淆。题目发布前运行参考解、边界输入和回归测试。

### 14.3 插件协议和判题测试

覆盖 handshake 超时、重复消息、消息乱序、非法序列号、不受信任来源、iframe 重载、宿主不支持能力、Worker 重启恢复、服务端重放一致性、权限校验、限流、超时和资源限制。

### 14.4 UI、无障碍和部署测试

至少覆盖 320、375、768、1024、1440 和 1920 宽度；Chrome、Firefox 和 Safari；主题切换、键盘操作、reduced-motion、高对比度、非根路径部署、受限 CSP、无后端环境和网络中断后的本地运行。自动化无障碍检查不能替代键盘和屏幕阅读器抽样验证。

### 14.5 计划书层面的验收标准

MVP 验收应同时满足：

- 原始产品定位、教学动机、Web 插件形态和框架化扩展方向没有被削弱；
- 至少一条完整的“输入字节到目标条件”的教学闭环可以演示；
- 题目可以通过受限格式加载、校验和版本化；
- 浏览器端状态与服务端重放职责清晰；
- 失败结果能够解释，而不是只返回通用错误；
- 关键状态可以单步、回退和重放；
- 运行时、插件协议和判题边界有对应测试；
- 性能数字经过目标设备 benchmark 后再确定是否达标。

## 十五、风险、取舍与应对措施

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 范围膨胀为完整 CPU/OS 模拟器 | 延迟 MVP，增加安全和测试成本 | 固定栈帧、buffer、return address 闭环，复杂能力后置 |
| 原文定位被技术细节稀释 | 产品目标失焦 | 所有技术章节回扣初学者教学因果链 |
| DSL 逃逸到宿主环境 | 可能造成代码执行或数据访问风险 | Schema、静态检查、受限 IR、白名单 Runtime 和资源预算 |
| 客户端篡改状态或成绩 | 正式成绩不可信 | 服务端只接收动作并独立重放，不信任前端最终状态 |
| iframe 与跨域策略不兼容 | 平台接入失败 | 独立来源、版本化协议、明确 origin 校验和接入 Demo |
| 回放不确定 | 争议无法复现，题目升级可能改变结果 | 固定 seed，记录题目/引擎/Profile/判题版本和状态哈希 |
| Worker 通信或 UI 更新过多 | 卡顿、暂停响应慢 | 批量 `VmDelta`、dirty page、rAF 合帧和局部更新 |
| 过早引入 WASM 等低层优化 | 增加复杂度但收益不确定 | 先完成 TypeScript 正确实现，以 benchmark 驱动优化 |
| 提示直接给出答案 | 学习者缺少独立分析过程 | 采用四级提示，不自动修正关键偏移和端序 |
| 低端设备性能不足 | 初学者体验不稳定 | Worker 隔离、分页、虚拟列表、降级策略和真实设备测试 |
| 题目质量不一致 | 学习路径断裂 | 发布前参考解、边界输入、题目回归和课程审核 |

## 十六、成功指标与后续运营观察

项目上线或试用后，建议观察以下指标，而不是只统计提交次数：

- 学习者从打开题目到首次成功的时间；
- 各题完成率和放弃率；
- 提示使用等级和回退次数；
- 错误类型分布及重复错误比例；
- 学习前后对地址、栈帧、端序和控制流的概念理解变化；
- 从插件加载到可交互的时间；
- CTF 平台接入所需时间；
- 出题人制作、校验和调试一题所需时间；
- 低端设备上的暂停响应、内存占用和回放性能；
- 服务端重放失败、协议错误和题目配置错误数量。

这些指标用于验证“提升新生水平与兴趣”的目标，并决定是否进入高级能力扩展，而不是把尚未验证的数字写成既定承诺。

---

## 十七、四条必须坚持的底线

1. **题目 DSL 不执行任意宿主代码。**
2. **浏览器端不负责最终计分。**
3. **默认使用独立来源 iframe。**
4. **VM Core、UI、插件协议和 CTF 平台适配层解耦。**

这四条底线同时是安全边界、架构边界和后续可扩展性的基础。
